# 会话

一次对话 = 一个会话。这份文档讲会话在磁盘上怎么存、界面上怎么列与切换、
归档和删除到底动了什么。

## 一、pi 的会话是怎么存的

pi 把**每个会话存成独立的 `.jsonl` 文件**：

```
~/.pi/agent/sessions/<cwd 编码后的目录名>/<时间戳>_<id>.jsonl
```

（`PI_CODING_AGENT_DIR` 可以改掉 agent 目录的位置。）

文件第一行是 header：

```json
{"type":"session","version":3,"id":"…","timestamp":"…","cwd":"C:\\path\\to\\project"}
```

后面每行是一条条目。**消息体是嵌在 `message` 字段下的**：

```json
{"type":"message","id":"…","parentId":"…","timestamp":"…",
 "message":{"role":"user","content":[{"type":"text","text":"…"}]}}
```

不是顶层的 `role` / `content`。这一条踩过坑：第一版按顶层读，14 条消息里
一条标题都抽不出来。现在两种形状都认，免得 pi 换格式时又静默失效。

会话还**不只是一条消息链**，它是一棵 append-only 的条目树（每条有 `parentId`），
所以可以从任意节点分叉。见第九节。

## 二、为什么 Pi GUI 要自己列会话

pi 的 RPC 里有 `switch_session`（收一个会话文件路径），
**但没有任何「列出会话」的命令** —— 它 TUI 的 picker（`pi -r`）不对外。

所以列表只能 Pi GUI 自己扫目录得到。

### 「新对话之后旧对话就找不到了」—— 这个缺口是怎么来的

Pi GUI 一开始只有「新对话」（RPC `new_session`），却**没有任何入口切回旧会话**。
用户点一下，旧对话就从界面上消失了。

**对话从来没丢**：`new_session` 只换了 pi 进程内存里的当前会话，
磁盘上一个字节都没动。修法是新增会话列表 + 用 `switch_session` 切回去。

> ⚠️ 顺带一个 pi 的行为：**会话没有内容时 pi 不落盘**。`new_session` 之后
> `get_state` 已经给出了新的 `sessionFile`，但那个文件要等第一条消息才写。
> 只按磁盘文件列的话，刚开的空会话不在列表里 ⇒ 界面上「当前项」仍然是旧会话，
> 而当前项是不给点的 ⇒ **用户再也回不到旧对话**。
> 所以列表里会补上 pi 报的当前会话，标成 pending。

## 三、列表是怎么来的

`server/sessions.js` 扫 `<agentDir>/sessions/`：

1. **目录名只用来缩小扫描范围**。pi 的编码规则是
   `'--' + cwd.replace(/[\\/:]/g, '-') + '--'`，但那是 pi 的实现细节 ——
   猜不到就退回全量扫描。
2. **归属判定只认会话文件 header 里的 `cwd`**，不认目录名。
   目录名变了也不该让两个项目的对话串在一起。
3. **标题取第一条用户消息** —— 那是人一眼能认出「这是哪次对话」的东西，
   比文件名和时间戳有用得多。
4. 按更新时间倒序，最多 200 条。

会话文件读不出来（坏 JSON、被别的程序占着）**只影响它自己**：
在列表里跳过并给一条诊断，不让一个坏文件把整个列表打不开。

## 四、当前会话与 pending 会话

**当前会话从 pi 那里问**（`get_state` 给 `sessionFile`），不靠猜 ——
「界面显示的是哪个会话」只有 pi 自己说了算。

**pending 会话**是「pi 说它是当前会话，但磁盘上还没有这个文件」的那一条
（见第二节的说明）。它在界面上显示成斜体的「新会话（还没有消息）」，
并且：

- **不能切换**（切过去没有意义，你已经在里面了）
- **不能归档**、**不能删除**（没有文件可操作）

发出第一条消息后它就变成正常的一条。

## 五、切换

点列表里的一条即切。三条规矩：

1. **只传后端给的稳定 ID**，不传路径。后端在自己的索引里解析真实路径，
   并核对那条会话确实属于当前项目 ⇒ 不可能切到别的项目的会话上。
2. **切换后必须清界面再重建**（`afterSessionSwitch()`：清对话区 + 清变更账本 +
   `boot()`）。不这么做的话，切完界面还挂着上一个会话的消息，看着像「切了没生效」。
3. **正在流式输出时不给切** —— 切走会让那一轮的回答悬在半空。

⚠️ **会话一变就必须重画侧栏列表**（新开 / 分叉 / 用户切换）。
列表原本只在渲染项目列表时画一次，而这三条路径都不触发它 —— 于是列表停在
旧状态：旧会话仍然带着「当前」标记，而当前项是不给点的，用户就再也回不到
那条对话。这就是「开个新对话，旧对话就消失了」的真正原因。

## 六、命名

改名走 pi 的 RPC `set_session_name`，而**它只作用于当前会话**。
所以铅笔只出现在当前会话那一条上、悬停才显形 —— 不做「给任意会话改名」
这种做不到的按钮。改名是行内输入框，不是弹窗。

## 七、归档

归档是**可逆的组织动作**：会话文件原地不动，pi 那边完全不知道，
**只影响 Pi GUI 这个列表**。

所以归档**不会改变 `pi --continue` 会接着哪个会话** —— 这是有意为之：
「归档」是纯组织动作，不该让 pi 的行为变得不可预测。

被归档的收进「已归档 N 条」折叠组，点开才看得到。
**正在进行的会话不能归档** —— 先切到别的会话再归档。

## 八、删除

删除是**软删除**：文件被移进 Pi GUI 的回收站目录，**不是 `unlink`**。
会话文件是真实的对话记录，一次误点不该是不可逆的。

```
%APPDATA%\Pi GUI\trash-sessions\<会话 id>.jsonl
```

同时把「原来是谁、哪个项目、多少条消息、什么时候删的」记进
`%APPDATA%\Pi GUI\session-flags.json`，所以事后想找回是查得到的。
（`PI_GUI_DATA` 可以改掉这个数据目录。）

- 删除要过**二次确认**，文案里明说「文件不会被抹掉」
- **正在进行的会话不能删除** —— pi 正开着那个文件往里追加
- 归档记录用 pi 的 `sessionId`（header 里的 UUID）当键，而不是我们那个
  「路径 sha1」ID：前者跟着会话走，文件挪了位置也不会失配

## 九、分支与分叉

pi 的会话是一棵 **append-only 的条目树**，每个节点都能「从此处分叉」
（`fork`），开一条新支线。这是 pi 相对普通聊天界面最有价值的差异点。

侧栏「分支」列出当前会话里**可回溯的对话节点**，点一条即从该处分叉：

- **只列参与对话的条目**（`message` / `custom_message`）。
  切换模型、调整思考档位、用量、上下文编辑这类**操作**不列 ——
  它们不是对话内容，列出来只会把真正的提问淹没。
- ⚠️ 隐藏节点时，它的子节点会**上提到最近的可见祖先**。pi 的条目是一条
  `parentId` 链，一次切换模型夹在两条消息中间，直接跳过整棵子树会把后面
  整段对话切掉。
- **全部左对齐**，不按深度递进缩进（原来每深一层往右 12px，长会话一路斜到
  右边，而 pi 的链大多是直的，阶梯没有信息量）。只在**分叉点**标出支线数。
- 节点文本截到 56 字，悬停给出完整那行。
- 节点文本按条目类型取字段：`message` 的消息体在 `entry.message` 里
  （不是顶层），取不到就会渲染成 `message: [object Object]`。

## 十、会话内提问导航（Conversation Minimap）

聊天区左边一列低对比度短线，**每条对应一次用户提问**。
hover 看摘要、点击平滑跳过去、滚动时当前那条自动高亮。

- **只画用户消息**：assistant / tool / thinking 都不画点（否则变成刻度尺）
- **位置按内容比例映射**：`top = 消息在内容里的偏移 / scrollHeight × 容器高`，
  不是按序号均分
- **DOM 是唯一权威**：导航只持有 `{id, element, marker, preview}`，
  历史重建 / 分叉 / 重试 / 切项目后一律重新扫 DOM，不存消息副本
- **滚动路径无布局读取**：位置缓存 + 二分；IntersectionObserver 只当
  「有 anchor 越过顶部带」的触发器

> 维护提醒：jsdom **没有** IntersectionObserver（缺它时要退回 rAF 节流的滚动
> 判定，否则 smoke 直接崩），也**不做布局**（`getBoundingClientRect()` 恒为 0，
> 位置类断言必须先给几何量打桩）。

## 十一、会话全文搜索（P3）

一个项目用久了会攒下几十上百个会话，「我以前问过什么」就再也没有入口了。
搜索框就在**当前项目的会话区域里**（列表上方），不是一个单独的搜索面板 ——
会话属于项目，搜索也一样。

- **搜索范围**：会话标题、用户消息正文、assistant 的**文本**正文。
- **只搜当前项目。** 归属判定与列表**共用同一处**（`header.cwd` 校对），
  不是另写一份 —— 两份判定迟早会漂，漂掉的那份就是跨项目读取的口子。
- **默认不索引**：toolResult 的大块输出、图片 base64、附件二进制、thinking、
  toolCall 参数、system prompt、项目指令、planner 执行日志。
  做法上只取 `content` 里 **`type === 'text'`** 的片段 —— 上面那些是别的 type，
  自然进不来（不是靠黑名单，所以 pi 以后加新类型也不会漏进来）。
- **范围筛选**：活跃（默认）/ 已归档 / 全部。
- **已删除的会话不参与搜索。** 软删除是把文件**移出** sessions 目录，所以结构上
  就搜不到；另外还按 flags 再挡一道，防止文件被手工挪回目录里复活。
- **匹配**：英文大小写不敏感，中文直接子串匹配。**不是** AI / embedding 语义
  搜索，也不做模糊匹配 —— 「确定、可解释、无第三方依赖」是这一版的目标。
- **不暴露绝对路径**：响应里只有稳定 ID（路径 sha1 前 16 位）与 pi 的 `sessionId`，
  连 `.jsonl` 文件名都不回。
- **上限**（超出只是截断，不报错）：单会话最多读 8 MB、单次总读取 48 MB、
  最多 30 个会话 × 每个 5 条命中、snippet 最长 160 字。
  读不出来的文件会计进 `scanned.skipped`（**可见**，不是静默丢掉）。
- **缓存**：解析结果按**文件路径**缓存，判据是 `mtime + size`。六个失效要求因此
  都是结构性的 —— 改文件会重读、rename 换键、archive 每次现读 flags、delete 后
  文件已不在扫描范围、新会话必然未命中、切项目只查当前项目扫出来的文件。

接口：`GET /api/sessions/search?q=…&scope=active|archived|all`

### 点结果之后怎么定位到那条消息

1. 用现有的安全接口切会话（只传稳定 ID）
2. 等**历史真正渲染完成**
3. 滚到命中的那次提问

第 2 步原来**没有信号** —— `afterSessionSwitch()` 只是 `setTimeout(boot, 250)`，
之后还要等 `get_messages` 一个来回。所以 `messages.js` 补了一个明确的
**生命周期回调**（`setAfterHistoryRendered`），在历史重建 + 导航重建之后触发。
监听方返回 `true` 表示「这次位置由我决定」，调用方就不再滚到底 ——
否则 `scrollBottom` 那一帧 rAF 会把刚定位好的位置又拉回最底
（用户看到的是「跳转没生效」）。

第 3 步**复用已有的 minimap 锚点表**，不另做一套滚动定位系统。
定位用的是**第几次用户提问**（`userIndex`），不是消息 ID —— 前端的
`data-nav-id` 是渲染时按顺序现发的计数器（`msg-N`），跨重建不稳定；
而「第 N 次提问」在「后端扫文件」与「DOM 里第 N 条 `.msg.user`」两边语义一致。
assistant 的命中归到**它前面那次提问**上，定位精度就到提问这一级 ——
不为了精确到消息去改消息模型。

### 刷新与并发

- 输入 **debounce 220 ms**；少于 2 个字符不发请求（给提示）；空关键词直接
  回到普通列表。
- 请求带 `searchRequestId` + 发起时捕获的 `S.workspaceGeneration`，
  渲染前**两次校验**：
  - 递增的请求号挡住「abcd 先回来、abc 后回来」；
  - 工作区代号挡住「在 A 项目搜索、切到 B、A 的结果才回来」。
  两者挡的是**两类不同的竞态**，缺一不可。
- 后端每处理 20 个会话让出一次事件循环 —— 否则几百个大会话会把事件循环
  按住几百毫秒到几秒，界面输入跟着卡。

## 十二、安全边界

- 前端只拿得到**稳定 ID**（路径的 sha1 前 16 位），拿不到也传不了绝对路径
- 切换 / 归档 / 删除都只传 ID，后端在索引里查真实路径，并核对 `cwd`
- 列表响应里**不含任何绝对路径**（不回 `currentFile`、不回 `cwd`）
- **归档与回收站是 Pi GUI 自己的状态**，落在 `<PI_GUI_DATA>/`，
  **不往 pi 的目录里塞任何东西**
- 搜索同理：只传关键词与范围，**不传路径**；搜索读取前会 realpath 一次，
  解析到 sessions 根之外的（symlink 越界）直接跳过

## 十三、数据目录

| 路径 | 内容 |
|---|---|
| `<PI_GUI_DATA>/session-flags.json` | 归档列表 + 已删除记录（原子写） |
| `<PI_GUI_DATA>/trash-sessions/` | 被删除的会话文件 |

`session-flags.json` 坏掉时一律当空的 —— 不能让一个坏文件把整个列表打不开。

## 十四、相关测试

`npm run test:sessions`（77 条）：目录名编码、单个会话文件的解析（含两种消息体
形状）、列表与归属判定、安全边界（未知 id / 路径穿越 / 跨项目 id 一律拒绝）、
切换与改名的降级、归档与删除（当前会话拒绝、软删除进回收站、flags 原子写、
坏 flags 不拖垮列表）、「当前会话还没落盘时补位」、HTTP 路由。

`npm run test:search`（71 条）：标题 / 用户正文 / assistant 正文、英文大小写、
中文、active / archived / all、deleted 不出现、坏文件不拖垮整体、跨项目不出现、
响应不含绝对路径与文件名、snippet 上限与折空白、结果与读取上限、关键词过短不读盘、
改名后标题更新、`userIndex` 归属、缓存失效、HTTP 层与路由顺序
（`/api/sessions/search` **必须排在 `/api/sessions/` 前缀之前**），
以及 200 个会话下的性能边界（事件循环停顿 / 堆增长 / 读取预算）。

前端（`npm run test:ui`）：搜索框在会话区域内、空关键词不请求、debounce、
正在搜索 / 没找到 / 失败三态、结果渲染与归档标记、snippet 走文本节点
（桩里塞了 `<img onerror>`，必须原样显示成文本、DOM 里不能真出现 img）、
点结果切会话并**定位到第 N 次提问**、旧请求被丢弃、切项目后清空。

全程在 `os.tmpdir()` 里造 fixture，**绝不碰真实的 `~/.pi/agent/sessions`** ——
这一点是硬要求：开发这个模块时就是因为拿真实项目测「改名」，把用户的一个
会话文件追加了一行。**会写盘的用例一律用临时 fixture。**
