# 会话

一次对话 = 一个会话。这份文档讲会话在磁盘上怎么存、界面上怎么列与切换、
归档和删除到底动了什么。

## 一、pi 的会话是怎么存的

pi 把**每个会话存成独立的 `.jsonl` 文件**：

```
~/.pi/agent/sessions/<cwd 编码后的目录名>/<时间戳>_<id>.jsonl
```

（`PI_CODING_AGENT_DIR` 可以改掉 agent 目录的位置。）

文件第一行是 header：

```json
{"type":"session","version":3,"id":"…","timestamp":"…","cwd":"C:\\path\\to\\project"}
```

后面每行是一条条目。**消息体是嵌在 `message` 字段下的**：

```json
{"type":"message","id":"…","parentId":"…","timestamp":"…",
 "message":{"role":"user","content":[{"type":"text","text":"…"}]}}
```

不是顶层的 `role` / `content`。这一条踩过坑：第一版按顶层读，14 条消息里
一条标题都抽不出来。现在两种形状都认，免得 pi 换格式时又静默失效。

会话还**不只是一条消息链**，它是一棵 append-only 的条目树（每条有 `parentId`），
所以可以从任意节点分叉。见第九节。

## 二、为什么 Pi GUI 要自己列会话

pi 的 RPC 里有 `switch_session`（收一个会话文件路径），
**但没有任何「列出会话」的命令** —— 它 TUI 的 picker（`pi -r`）不对外。

所以列表只能 Pi GUI 自己扫目录得到。

### 「新对话之后旧对话就找不到了」—— 这个缺口是怎么来的

Pi GUI 一开始只有「新对话」（RPC `new_session`），却**没有任何入口切回旧会话**。
用户点一下，旧对话就从界面上消失了。

**对话从来没丢**：`new_session` 只换了 pi 进程内存里的当前会话，
磁盘上一个字节都没动。修法是新增会话列表 + 用 `switch_session` 切回去。

> ⚠️ 顺带一个 pi 的行为：**会话没有内容时 pi 不落盘**。`new_session` 之后
> `get_state` 已经给出了新的 `sessionFile`，但那个文件要等第一条消息才写。
> 只按磁盘文件列的话，刚开的空会话不在列表里 ⇒ 界面上「当前项」仍然是旧会话，
> 而当前项是不给点的 ⇒ **用户再也回不到旧对话**。
> 所以列表里会补上 pi 报的当前会话，标成 pending。

## 三、列表是怎么来的

`server/sessions.js` 扫 `<agentDir>/sessions/`：

1. **目录名只用来缩小扫描范围**。pi 的编码规则是
   `'--' + cwd.replace(/[\\/:]/g, '-') + '--'`，但那是 pi 的实现细节 ——
   猜不到就退回全量扫描。
2. **归属判定只认会话文件 header 里的 `cwd`**，不认目录名。
   目录名变了也不该让两个项目的对话串在一起。
3. **标题按来源优先级取**：显式采纳 / 原生手动名 > AI 自动标题 > 首条用户消息
   > 默认「（还没有消息）」。首条用户消息仍然是最原始的兜底 —— 那是人一眼能
   认出「这是哪次对话」的东西，比文件名和时间戳有用得多。AI 标题的归属、
   持久化与失败边界见第六节后的「AI 自动标题」。
4. 按更新时间倒序返回全部会话。不按数量截断 —— 数量上限会让较早的记录
   永远无法出现在列表里；渲染成本由前端滚动与分批 DOM 承担。

会话文件读不出来（坏 JSON、被别的程序占着）**只影响它自己**：
在列表里跳过并给一条诊断，不让一个坏文件把整个列表打不开。

侧栏用项目标题分组，会话前有装饰圆点、标题单行截断，当前会话整行灰色高亮。
时间与消息数量放在悬停提示里。标题区域的箭头 / 文件夹图标 / 名称 / 空白是同一个展开收起按钮；每个项目行都有加号复用新对话，侧栏顶部的搜索图标 toggle 会话搜索；三点菜单继续使用原有项目与会话操作。切换项目只留在项目菜单的「切换到此项目」里，普通标题点击不承担切换。

每个项目都有独立展开按钮，多个项目可以同时展开。本次运行中记住展开状态，
其它项目首次出现时默认收起，当前项目首次出现时默认展开。展开预览不重启 Pi、
不切换聊天。`GET /api/sessions?project=…` 只接受已添加项目，复用同一处 header.cwd
归属校验；预览其它项目时不向 Pi 请求状态，也不伪造当前或 pending 会话。
预览列表显示活跃会话；查看归档或执行会话操作前先打开该项目的会话。

点击其它项目的会话会先激活项目，等待 Pi 就绪并完成状态同步，再通过既有
`switch_session` 路径打开它。队列绑定工作区代号，新一次项目切换会取消旧动作。

## 四、当前会话与 pending 会话

**当前会话从 pi 那里问**（`get_state` 给 `sessionFile`），不靠猜 ——
「界面显示的是哪个会话」只有 pi 自己说了算。

**pending 会话**是「pi 说它是当前会话，但磁盘上还没有这个文件」的那一条
（见第二节的说明）。它在界面上显示成斜体的「新会话（还没有消息）」，
并且：

- **不能切换**（切过去没有意义，你已经在里面了）
- **不能归档**、**不能删除**（没有文件可操作）

发出第一条消息后它就变成正常的一条。

## 五、切换

点列表里的一条即切。三条规矩：

1. **只传后端给的稳定 ID**，不传路径。后端在自己的索引里解析真实路径，
   并核对那条会话确实属于当前项目 ⇒ 不可能切到别的项目的会话上。
2. **切换后必须清界面再重建**（`afterSessionSwitch()`：清对话区 + 清变更账本 +
   `boot()`）。不这么做的话，切完界面还挂着上一个会话的消息，看着像「切了没生效」。
3. **正在流式输出时不给切** —— 切走会让那一轮的回答悬在半空。

⚠️ **会话一变就必须重画侧栏列表**（新开 / 分叉 / 用户切换）。
列表原本只在渲染项目列表时画一次，而这三条路径都不触发它 —— 于是列表停在
旧状态：旧会话仍然带着「当前」标记，而当前项是不给点的，用户就再也回不到
那条对话。这就是「开个新对话，旧对话就消失了」的真正原因。

## 六、命名

会话三点菜单统一显示「AI 生成标题 / 重命名 / 归档（或取消归档）/ 删除会话」。
**重命名不再要求先打开会话**：当前会话、未打开的历史会话、已归档会话、
其它项目的预览行都能在自己的行内直接改名。请求只带稳定身份
（经典：项目路径 + 会话 id；Runtime：conversationId）与期望修订号，
由后端受信解析器证明真实文件；Renderer 不提交文件路径，也不为改名
`switch_session`、新建会话、重启 Pi 或打断正在运行的回合。
改名是行内输入框（Enter 保存、Escape 取消、失焦保存合法改动、空白不提交），
不是第二套弹窗；成功后行、顶部（如果正是当前会话）、搜索结果与 Runtime 视图
一起就地更新，不重排列表、不抖滚动位置。

「AI 生成标题」与手动重命名是两件事，但共用同一个标题存储与修订号：
前者写自动 / 采纳的 AI 标题，后者写用户手动标题。`sessionNaming`
（Pi 原生改名能力）不可用时不再禁用本功能的重命名 —— 这条路径只写
Pi GUI 自己的元数据，不依赖 Pi 的 `set_session_name`。pending 会话尚未落盘，
仍不显示菜单。**外部 Pi 看不到 pi-GUI 里的手动标题**：本功能从不写 Pi 的
JSONL；Pi 自己仍以它的 `session_info.name` 为准。

### AI 自动标题（与手动标题的优先级）

**来源与优先级**（`server/session-title-store.js` 统一裁决）：

1. **Pi GUI 手动标题**：用户在侧栏 / 顶栏手动改的名，或在「AI 生成标题」的
   确认框里显式采纳的覆盖。
2. **Pi 原生手动名**（`session_info.name`，用户用 Pi 的 `set_session_name`
   起的名字）。只有当前确认到的原生名与 pi-GUI 手动标题记录时的快照一致时，
   手动标题才继续获胜；原生名一旦变化（用户在 Pi 里改名），旧手动标题失效，
   原生名按优先级重新获胜。**「原生名未知」不等于「原生名为空」**：若写入
   手动标题时文件被截断、尾部没能确认到原生名，记录会标成
   `nativeNameConfirmed=false`；之后列表或 `get_state` 确认到的第一个原生名
   只补进快照并保留手动标题，不会被误判成用户刚在 Pi 里改名。
   Runtime 记录的 `sessionName` 可能是 pi-GUI 自己的显示种子（`nameSource=seed`），
   只有 `get_state` 真正观察过的名字才升级为 `native`，种子不能当原生确认。
3. **AI 自动标题**（本功能生成，存在 Pi GUI 自己的数据目录）。
4. **首条用户消息**（临时兜底；发出首条消息后立即显示，AI 标题回来后替换）。
5. **默认标题**「（还没有消息）」/「并行会话」。

**修订号（revision）是唯一裁决依据**：存储里每条标题记录都有持久化的
`revision` 与原生名快照；自动生成、手动生成、重命名、确认采纳共用同一个
修订契约。所有写入都携带 `expectedRevision`，不匹配返回
`revision_conflict` 与当前权威标题 / 修订号；前端 `title-revision.js`
按同一门槛丢弃迟到的 SSE、旧列表快照与旧切换应答（低修订丢弃，
同修订不同内容也丢弃，只有同修订同内容幂等）。只有原生名、还没有标题
记录的会话也会建立内存修订锚点（`revision=1`），原生名再变时递增，避免
「列表扫描与生成之间改名」逃过修订比较；锚点只随后续真实写入落盘，
启动扫描不会逐条写盘，容量清理时可回收。

自动标题只在**首轮成功且非空、非中断**后触发一次：读会话文件确认首条是用户消息、
首轮有有效回复、没有原生手动名、不是恢复 / 分叉会话、会话创建时间晚于设置开启时间。
首轮失败 / 中断 / 只有工具过程文本 / 被截断时，等后续第一条**正常完成**的
有效回复，并取那条回复实际使用的 provider/model；不把后面的无关模型选择、
thinking、toolResult 或部分输出当成首条回复。
没有有效回复时等后续第一条有效回复；失败 / 输出不合格只记录一次 attempt，
保留临时标题，不重试、不阻塞聊天。开关关闭会作废在途自动任务。

**归属**：生成开始时捕获目标文件、header id、原生名快照、文件身份与
`baseRevision`；应用前再读同一文件核对原生名，并比较存储修订。
期间删除 / 归档 / 移动 / 恢复、在 Pi 里改名、手动重命名、文件身份变化都会让
迟到结果被丢弃；**切换会话或切换模型不会改变已捕获的目标**：结果仍只写原目标，
不会写到当前选中的会话上。经典会话与 Runtime 并行会话都支持（Runtime 文件要等
`refreshSession` 证明已落盘后才触发）。会话文件超过 4MB 时，头部只读前 4MB，
再从尾部 512KB 确认最新的 `session_info.name`；尾部确认不到就标记
`nativeConfirmed=false`，交给标题裁决保守处理，**绝不把「截断没读到」当成
「用户没有改过名」**。

**持久化**：`<DATA_DIR>/session-titles.json` 与 `session-title-settings.json`
（原子写，0600）。**从不写 Pi 的 `.jsonl`**，也不把后台会话切为当前来保存标题。
Pi 的 JSONL 仍只由 Pi 追加；原生名仍以 Pi 的 `session_info` 为准。
容量上限只清理「只有 attempt、没有有效标题」的记录；有效的自动 / 手动标题
不因条数被删除。

**模型调用**：`server/session-title-sdk.js` 在隔离 worker 里加载 Pi 公开的
`ModelRuntime`，用产生首条回复的 provider/model 调一次 `completeSimple`
（约 1000–1200 字符素材、`maxTokens: 64`、`reasoning: 'minimal'`、无工具、
`maxRetries: 0`）。复用 Pi 现有 API Key / OAuth / 订阅 / 自定义模型认证，
不额外要 key，不带 `PI_GUI_TOKEN`，不把回复或错误原文带回主进程。
worker 身份包含 auth / models 文件的 `mtimeMs:size` 指纹，用户在 Pi 里登录、
切换订阅或修改 provider 配置后，下一次标题调用会重建 worker，不继续持有
过期凭据或旧模型表。每次自动标题会消耗少量模型用量；设置页对此有说明。
当前 Pi 不提供该能力时安全降级，手动入口与设置项按能力三值处理
（未知照常显示，明确不支持才隐藏 / 禁用）。

**设置**：「常规」页的「自动生成会话标题」默认开启，只对开启后新建的会话生效，
不批量补历史会话；「标题生成模型」当前固定为「跟随当前会话」，不提供假的模型选择器。
手动入口在经典会话行与 Runtime 并行会话行的三点菜单，均复用同一个生成服务；
自动开关关闭时仍可用，目标不必是当前正在查看的会话。顶部标题的重命名也走
同一个 `/api/session-titles/rename`，不再直连 Pi 的 `set_session_name`
（只有尚未落盘的 pending 当前会话保留原生改名作为兼容退路）。

验收与实测范围见 [ai-session-title-acceptance.md](ai-session-title-acceptance.md)；
测试入口是 `npm run test:session-title-ai`。

## 七、归档

归档是**可逆的组织动作**：会话文件原地不动，pi 那边完全不知道，
**只影响 Pi GUI 这个列表**。

所以归档**不会改变 `pi --continue` 会接着哪个会话** —— 这是有意为之：
「归档」是纯组织动作，不该让 pi 的行为变得不可预测。

被归档的收进「已归档 N 条」折叠组，点开才看得到。
**正在进行的会话不能归档** —— 先切到别的会话再归档。

## 八、删除

删除是**软删除**：文件被移进 Pi GUI 的回收站目录，**不是 `unlink`**。
会话文件是真实的对话记录，一次误点不该是不可逆的。

```
%APPDATA%\Pi GUI\trash-sessions\<会话 id>.jsonl
```

同时把「原来是谁、哪个项目、多少条消息、什么时候删的」记进
`%APPDATA%\Pi GUI\session-flags.json`，所以事后想找回是查得到的。
（`PI_GUI_DATA` 可以改掉这个数据目录。）

- 删除要过**二次确认**，文案里明说「文件不会被抹掉」
- **正在进行的会话不能删除** —— pi 正开着那个文件往里追加
- 归档记录用 pi 的 `sessionId`（header 里的 UUID）当键，而不是我们那个
  「路径 sha1」ID：前者跟着会话走，文件挪了位置也不会失配

## 九、分支与分叉

pi 的会话是一棵 **append-only 的条目树**，每个节点都能「从此处分叉」
（`fork`），开一条新支线。这是 pi 相对普通聊天界面最有价值的差异点。

侧栏「分支」列出当前会话里**可回溯的对话节点**，点一条即从该处分叉：

- **只列参与对话的条目**（`message` / `custom_message`）。
  切换模型、调整思考档位、用量、上下文编辑这类**操作**不列 ——
  它们不是对话内容，列出来只会把真正的提问淹没。
- ⚠️ 隐藏节点时，它的子节点会**上提到最近的可见祖先**。pi 的条目是一条
  `parentId` 链，一次切换模型夹在两条消息中间，直接跳过整棵子树会把后面
  整段对话切掉。
- **全部左对齐**，不按深度递进缩进（原来每深一层往右 12px，长会话一路斜到
  右边，而 pi 的链大多是直的，阶梯没有信息量）。只在**分叉点**标出支线数。
- 节点文本截到 56 字，悬停给出完整那行。
- 节点文本按条目类型取字段：`message` 的消息体在 `entry.message` 里
  （不是顶层），取不到就会渲染成 `message: [object Object]`。

## 十、会话内提问导航（Conversation Minimap）

聊天区左边一列低对比度短线，**每条对应一次用户提问**。
hover 看摘要、点击平滑跳过去、滚动时当前那条自动高亮。

- **只画用户消息**：assistant / tool / thinking 都不画点（否则变成刻度尺）
- **marker 聚成一组紧凑短线**（UX 修复）：整组纵向居中，条数与可用高度决定
  短线高度与间距（10～40 条时是一组连续的短线，长会话按可用高度压缩间距，
  绝不越出容器）。顺序仍然是「第 1 次提问 → 第 1 条」。
  早先是 `top = 消息在内容里的偏移 / scrollHeight × 容器高` —— 一条很长的
  assistant 回答会把后面的点推到很远，marker 散满整个左栏、很难连续点。
- **点击跳转只写 `#stream.scrollTop`**（`scrollTo({top, behavior:'smooth'})`），
  **不用 `element.scrollIntoView()`**：后者会连带滚动所有「可编程滚动」的祖先，
  而 `.stage` 是 `overflow:hidden`（hidden 只是不给用户滚动条，`scrollTop` 照样
  能被脚本改），于是点一下 marker 整个 workspace 会被推上去 46px、顶栏被推出
  视口。落点 = `topInContent - 20`，clamp 到 `[0, scrollHeight - clientHeight]`。
  回归测试在 `tests/smoke.cjs`（不许调用 scrollIntoView）与
  `tests/cdp-shot.cjs` 的 UX-06（跳转前后 `.stage-head` / `#chatView` / 输入区
  的矩形必须一个像素都不动）。
- **内容偏移仍然缓存**（`topInContent`）：跳转与「当前是第几条」都用它，
  只是不再决定 marker 的纵向位置
- **DOM 是唯一权威**：导航只持有 `{id, element, marker, preview}`，
  历史重建 / 分叉 / 重试 / 切项目后一律重新扫 DOM，不存消息副本
- **滚动路径无布局读取**：位置缓存 + 二分；IntersectionObserver 只当
  「有 anchor 越过顶部带」的触发器

> 维护提醒：jsdom **没有** IntersectionObserver（缺它时要退回 rAF 节流的滚动
> 判定，否则 smoke 直接崩），也**不做布局**（`getBoundingClientRect()` 恒为 0，
> 位置类断言必须先给几何量打桩）。

## 十一、会话全文搜索（P3）

一个项目用久了会攒下几十上百个会话，「我以前问过什么」就再也没有入口了。
搜索框就在**当前项目的会话区域里**（列表上方），不是一个单独的搜索面板 ——
会话属于项目，搜索也一样。

- **搜索范围**：会话标题、用户消息正文、assistant 的**文本**正文。
- **只搜当前项目。** 归属判定与列表**共用同一处**（`header.cwd` 校对），
  不是另写一份 —— 两份判定迟早会漂，漂掉的那份就是跨项目读取的口子。
- **默认不索引**：toolResult 的大块输出、图片 base64、附件二进制、thinking、
  toolCall 参数、system prompt、项目指令、planner 执行日志。
  做法上只取 `content` 里 **`type === 'text'`** 的片段 —— 上面那些是别的 type，
  自然进不来（不是靠黑名单，所以 pi 以后加新类型也不会漏进来）。
- **范围筛选**：活跃（默认）/ 已归档 / 全部。关闭搜索或切项目后回到活跃，范围按钮的选中态与 `aria-pressed` 同步复位。
- **已删除的会话不参与搜索。** 软删除是把文件**移出** sessions 目录，所以结构上
  就搜不到；另外还按 flags 再挡一道，防止文件被手工挪回目录里复活。
- **匹配**：英文大小写不敏感，中文直接子串匹配。**不是** AI / embedding 语义
  搜索，也不做模糊匹配 —— 「确定、可解释、无第三方依赖」是这一版的目标。
- **不暴露绝对路径**：响应里只有稳定 ID（路径 sha1 前 16 位）与 pi 的 `sessionId`，
  连 `.jsonl` 文件名都不回。
- **上限**（超出只是截断，不报错）：单会话最多读 8 MB、单次总读取 48 MB、
  最多 30 个会话 × 每个 5 条命中、snippet 最长 160 字。
  读不出来的文件会计进 `scanned.skipped`（**可见**，不是静默丢掉）。
- **缓存**：解析结果按**文件路径**缓存，判据是 `mtime + size`。六个失效要求因此
  都是结构性的 —— 改文件会重读、rename 换键、archive 每次现读 flags、delete 后
  文件已不在扫描范围、新会话必然未命中、切项目只查当前项目扫出来的文件。

接口：`GET /api/sessions/search?q=…&scope=active|archived|all`

### 点结果之后怎么定位到那条消息

1. 用现有的安全接口切会话（只传稳定 ID）
2. 等**历史真正渲染完成**
3. 滚到命中的那次提问

第 2 步原来**没有信号** —— `afterSessionSwitch()` 只是 `setTimeout(boot, 250)`，
之后还要等 `get_messages` 一个来回。所以 `messages.js` 补了一个明确的
**生命周期回调**（`setAfterHistoryRendered`），在历史重建 + 导航重建之后触发。
监听方返回 `true` 表示「这次位置由我决定」，调用方就不再滚到底 ——
否则 `scrollBottom` 那一帧 rAF 会把刚定位好的位置又拉回最底
（用户看到的是「跳转没生效」）。

第 3 步**复用已有的 minimap 锚点表**，不另做一套滚动定位系统。
定位用的是**第几次用户提问**（`userIndex`），不是消息 ID —— 前端的
`data-nav-id` 是渲染时按顺序现发的计数器（`msg-N`），跨重建不稳定；
而「第 N 次提问」在「后端扫文件」与「DOM 里第 N 条 `.msg.user`」两边语义一致。
assistant 的命中归到**它前面那次提问**上，定位精度就到提问这一级 ——
不为了精确到消息去改消息模型。

### 刷新与并发

- 输入 **debounce 220 ms**；少于 2 个字符不发请求（给提示）；空关键词直接
  回到普通列表。
- 请求带 `searchRequestId` + 发起时捕获的 `S.workspaceGeneration`，
  渲染前**两次校验**：
  - 递增的请求号挡住「abcd 先回来、abc 后回来」；
  - 工作区代号挡住「在 A 项目搜索、切到 B、A 的结果才回来」。
  两者挡的是**两类不同的竞态**，缺一不可。
- 后端每处理 20 个会话让出一次事件循环 —— 否则几百个大会话会把事件循环
  按住几百毫秒到几秒，界面输入跟着卡。

## 十二、安全边界

- 前端只拿得到**稳定 ID**（路径的 sha1 前 16 位），拿不到也传不了绝对路径
- 切换 / 归档 / 删除都只传 ID，后端在索引里查真实路径，并核对 `cwd`
- 列表响应里**不含任何绝对路径**（不回 `currentFile`、不回 `cwd`）
- **归档与回收站是 Pi GUI 自己的状态**，落在 `<PI_GUI_DATA>/`，
  **不往 pi 的目录里塞任何东西**
- 搜索同理：只传关键词与范围，**不传路径**；搜索读取前会 realpath 一次，
  解析到 sessions 根之外的（symlink 越界）直接跳过

## 十三、数据目录

| 路径 | 内容 |
|---|---|
| `<PI_GUI_DATA>/session-flags.json` | 归档列表 + 已删除记录（原子写） |
| `<PI_GUI_DATA>/trash-sessions/` | 被删除的会话文件 |

`session-flags.json` 坏掉时一律当空的 —— 不能让一个坏文件把整个列表打不开。

## 十四、任务会话的额外根目录

Planner 用 pi 跑任务时，会话落在 **`<PI_GUI_DATA>/planner-sessions/`**（平铺，
不再按 cwd 分子目录 —— `--session-dir` 指定的目录 pi 直接拿来用）。这是**刻意**与主会话
目录分开的：主聊天用 `--continue` 取该 cwd 下最近的会话，混进去会让用户下次聊天
莫名其妙接上某个任务的上下文。

代价是那些会话不在本模块的默认扫描范围里，于是「从任务打开会话」够不着它们。
P7 给了一个**只用于精确定位**的入口：注入的 `extraSessionRoots`。

- 它**不进 `ownedSessions()`** —— 那是「当前项目的会话列表」，把几十条任务会话混进侧栏
  只会把列表淹掉。任务会话只在「从任务跳过去」这一条路径上被解析。
- 解析出来之后走的还是**同一个** `switchToTarget` / `switch_session`，
  归属判定也复用同一套规则 —— 这不是第二套会话加载。
- 按 pi 的会话 id 定位时，先用**文件名**筛（pi 的命名是
  `<ISO 时间戳>_<encodeURIComponent(id)>.jsonl`），再读 header 核对 id 与 cwd。
  文件名只是线索，**归属仍然只认 header**（和列表同一条规矩）。

**归属判定的一处放宽（只作用于这条路径）**：任务的工作目录可以是子目录
（`workingDirectory: 'src'`），那种会话的 `header.cwd` 是 `<项目>/src`，
严格相等会把它判成「别的项目」。所以这条路径用「**在项目内**」。
侧栏列表用的仍是原有的严格相等规则，没有变松。

## 十六、Runtime 并行会话输入可靠性与草稿隔离（Z5-1）

对于右侧多会话与并行执行视图（Runtime Conversation），输入与草稿遵循以下独立隔离契约：

1. **中文输入法（IME）防护**：
   在 Runtime Composer 的本地作用域中监听 `compositionstart` 与 `compositionend`，守卫 `isComposing`、`keyCode === 229` 与组合状态。输入法候选词确认不误识别为 Enter 发送；`Shift+Enter` 换行不发送；会话切换和视图销毁时重置 composition 状态。
2. **草稿身份隔离**：
   持久化 key 只取后端快照已证明的稳定 locator：`projectId`、`workspaceId`、`workspaceEpoch`、`conversationId`、`nativeSessionId`。易变执行身份（`runtimeId`、`runtimeGeneration`）不进入 key，以支持同原生会话进程重启后的草稿恢复；`nativeSessionId` 或 `workspaceEpoch` 改变时严格隔离旧草稿。
3. **Owner 变化与 ACK 清理**：
   旧 Owner 的迟到 ACK 绝不清理新会话或用户新输入的草稿；仅当 ACK 属于当前目标会话、完整 Owner 匹配、draftRevision 与正文均等于提交版本时，才同步清除对应持久副本。
4. **容量与降级**：
   恢复上限为 20000 字符（`DRAFT_MAX_CHARS`）；超过 20000 字符时内存保留完整文本、清除持久副本并给出内联提示，不静默截断。存储配额不足或隐私模式时降级为仅内存保留并内联提示。

## 十七、并行执行与共享项目工具协调

Runtime Registry 已按会话持有独立 `session-runtime`、Pi child / guardian、RPC pending、
工具守卫与审批。Classic 聊天是另一条运行线；选中会话只决定显示，后台会话不会因切页而停止。
同一 Runtime 的重复 prompt 仍拒绝；不同 Runtime 的模型回合可以同时推进，不经过全局任务 FIFO。
pi-GUI 不设会话总量、独立 Runtime 或并行模型任务的数量上限：第三个及以后不需要确认，
也没有隐藏的软上限或并发设置。实际能开多少由操作系统资源、供应商能力和必要的身份 /
安全 / 维护 / 共享写协调决定；计数只用于展示与诊断，不参与准入。单个 Runtime 启动失败
只影响它自己，资源不足或供应商限流按真实错误呈现，不伪装成应用配额。

共享或父子重叠 workspace 的写工具仍由 `session-tool-scheduler.js` 协调，不因允许并行而绕过：

- 启动包的公开契约由同一 [工具协调 probe](pi-compatibility.md#会话工具协调契约2026-11-26-专项) 核验；
  版本号不决定可用性，source probe 为 true 也不等于 child 已 ready。
- 每个 child 还须完成私有 token + 原生 sessionId hello，后端用该 child 的 `get_state` 重验；
  证据缺失时提示工具写入协调未就绪，保留输入并 fail-closed，不把重启提示当作永久解决办法。
- 初始化通信失败在原握手内有限重试：扩展 single-flight 最多三次、总预算八秒且同一 controller
  内不重置；可证明的会话切换过渡只返回非授权的等待提示，不绑定会话、不解除保护，也不扩大
  预算。后端初始 binding 三十秒到期后终态失效，不靠新 prompt 或无限循环续命。可证明来自另一份实际存在的绝对路径
  扩展文件的 `extension_error` 不撤销本 guard；guard 自身、缺来源或无法核验的错误仍 fail-closed。
- 终态失效不承诺安全进程内恢复。输入保留，等待任务结束后由用户显式重启受影响 Runtime；
  新 generation 必须重新证明 owner、native sessionId、cwd、source 与当前 child。不会因此重启
  正常 B/C，也不会自动重发已提交但结果未知的任务；重启或 Stop 不能释放执行结果未知的 writer。
- 已证实来源的 builtin `read/ls/find/grep` 可按既有策略旁路写租约；未知工具与 Shell 保守等待。
  工具等待可以发生在 B，而 A/C 的模型请求、流式状态和独立项目工具继续推进。
- Stop/退出仅处置目标 owner 的资源；未确认清理不能提前释放活动写租约。重启恢复 dormant
  身份和历史，不复用旧进程、审批或迟到事件，也不自动续调模型。
- 普通项目的显式 restart/resume 重新走普通项目权限，而非 Worktree 身份解析；项目登记、
  目录 epoch、工具守卫和预算仍需通过。若 Classic 已续接同一个原生 session，独立 Runtime
  必须拒绝 `session_in_use`，不能让两个 child 同时写同一 Pi JSONL；恢复成功使用新的 owner。
- 所有异步准入结束后、创建 live/child 前同步复核已证明的 guard、owner 和 Classic 的
  cwd/session mutation epoch。私有切换应答可能不更新 owner 缓存，不能只靠缓存判断；
  RPC 原有命令账本中的会话变更在途（含超时但未确认终态）仍阻止新共享准入，直到权威应答或清理。

这是合作式工具调度，不是 OS sandbox、多文件事务或任意 Shell/Git 副作用的完整保护。
外部编辑、脱离工具生命周期的子进程、跨根访问和 Git 共享元数据仍需按实际边界处理。
本专项的修改范围、参考源码、真实模型与 Windows Electron 证据、未验证项和回滚见
[并行专项验收记录](parallel-runtime-acceptance.md)；当前行为说明不替代专项通过证明。
