# Windows 应用内更新

此功能由用户主动触发。发现新版本仍只显示设置入口提示，不弹窗、不下载。

在「设置 → 应用与更新」检查版本，阅读可独立滚动的更新说明，点击「下载并更新」。下载显示进度、平均速度，可取消、失败后重试。SHA256 验证完成才显示「重启以更新」；选择「稍后」保留缓存，下次启动离线重新校验本地包。Release 和手动下载入口始终保留。Pi 运行时更新仍是独立功能，可展开查看。

## 运行形态

| 形态 | 行为 |
| --- | --- |
| Windows NSIS 安装版 | 完整流程。当前 exe 的 realpath 必须匹配 HKCU 卸载记录 `InstallLocation\Pi GUI.exe`，且卸载程序存在。 |
| 便携版 / 无法确认的打包形态 | 下载并验证便携 ZIP，打开固定下载目录；退出后手动替换，不覆盖正在运行的 exe。 |
| 开发模式 / 其他平台 | 检查和手动 Release 链接，不执行自更新。 |

不得仅凭 `app.isPackaged`、exe 名字或位于 Programs 目录判断安装版。

## 权限与完整性

`server/update-check.js` 仍只负责发现；主进程通过已认证的本机 API 复用其结果。GitHub 地址、文件名、大小、版本和 SHA256 不来自 Renderer。IPC 仅暴露读取状态、下载、取消、打开便携包目录和请求安装；只接受主窗口的同源顶层 frame。安装前还会显示原生确认框。

资产必须是固定仓库 `HYJ1817/pi-gui`、精确的 `v<版本>` tag 和 `Pi-GUI-Setup-<版本>.exe`（或便携 ZIP），大小为正整数且不超过 1 GiB。下载只接受固定官方地址；每次重定向也必须是 GitHub Release 下载地址或 `release-assets.githubusercontent.com` / `objects.githubusercontent.com`。没有自定义更新源，也不转发令牌、Cookie、项目、会话或供应商数据。

优先使用公开 GitHub Release API 的 `sha256:` digest，缺失时只从相同版本的官方 `SHA256SUMS.txt` 取精确条目。安装前重新读取官方信息并比较 SHA，包括 checksum fallback，不能靠可修改的本地 manifest 建立执行信任。HTTPS/GitHub 账号是信任根；此机制不能抵御官方发布账号被接管，不替代既有签名与发布审批。

更新包位于当前用户临时目录 `pi-gui-updates`，先写 `.part`，验证成功才重命名并保存 `ready.json`。恢复缓存时重新计算文件 SHA256，过期版本不被当作可安装版本。目录 identity、文件类型和链接检查用于拒绝缓存路径替换。进程内下载单飞；外部助手还持有 OS 排他安装锁及安装包只读句柄。

## 安全退出

后端私有父子 IPC 承担维护控制，HTTP/Renderer 不能调用该通道。更新前检查：Classic 和全部 Runtime 活动、待处理审批、未应答命令及 RPC、停止屏障、认证、CLI、Pi/扩展更新、Planner/验证、托管进程、工具调度和文件变更 lease，以及未完成 HTTP 写请求。

任一项忙或无法确认时拒绝重启，提示等待，或先在对应会话安全停止。此版不提供强制终止升级。维护锁同步获取后禁止新 HTTP 写请求，关闭空闲 Runtime 并确认清理；Classic 仅关闭 stdin、等待退出，不走 `taskkill /F`。若退出无法确认，取消更新并恢复可用状态。

只有维护成功才启动位于安装目录之外的助手；后端实际退出后才写 armed 标记并调用应用退出。助手预先打开旧主进程句柄并核对启动时间，等待句柄结束，避免 PID 复用；关闭该句柄后，还必须证明 exe 已能排他写打开，不能把主进程退出误当作所有文件映射均已释放。正常关闭应用的既有退出行为不由此功能重新设计。

## 安装、恢复和重启

助手先重新计算 SHA256 并保持安装包只读句柄，再等旧应用完全退出。复制程序目录到该次临时更新目录下的 `backup`，然后使用固定参数 `/S /D=<当前安装目录>` 调用 NSIS。NSIS 静默路径遇仍运行实例返回 20，不强杀；无法覆盖文件返回 21，不出现隐藏确认框。

安装非零退出或安装后 package 版本不匹配时，用备份恢复原程序文件并重新启动旧版本。备份失败且程序文件未动时，确认旧 exe 的 hash 和路径未变再重启。保持原 userData 路径和数据相关环境；项目、会话、供应商、OAuth、草稿、设置及 Runtime 数据不被迁移或清空，AppData 不在备份/替换范围。新进程再将实际 `app.getVersion()` 与预期目标比较，只有匹配才显示完成。

助手尽力写固定错误阶段，不写底层异常原文或用户 payload；诊断写入失败不能改变等待或回滚顺序。启动恢复分为等待、成功、失败：助手持有排他安装锁（或无法确认锁已释放）时显示等待，主进程拒绝再次下载或安装，每 500 ms 离线复查；锁释放后，只有结果为 `installed` 且实际版本匹配才显示成功，缺少结果、版本不符或错误阶段显示失败。结果确认后仅清理对应 `pending.json`，提示保留在本次应用状态，下次启动不再重复。失败 UI 保留 Release 手动安装入口。程序文件备份和结果保留在该次临时目录，便于故障恢复；系统清理临时目录后需重新下载。

若磁盘故障使备份也不能恢复，记录 `recovery_required`，需手动重装程序；用户数据保持原处。若安装程序超过十分钟仍未退出，记录 `installer_timeout` 并保持锁等待它退出，不杀安装器、不与其并发回滚。断电、系统强制结束和真实签名后的下一版公网更新仍需发布前人工验收。

## 验证

```powershell
npm run test:app-update
npm run test:app-update:electron
npm run test:app-update:windows -- --previous-zip=<官方 v0.26.0 便携 ZIP 绝对路径>
node tests/app-update-windows-faults.cjs
```

默认专项完全离线，已纳入 `npm test` 的唯一测试链。Windows 验收不下载资产；输入 ZIP 必须匹配脚本内记录的官方 SHA256。所有写用例使用 `os.tmpdir()` 夹具；受限 Windows 测试仅给新夹具设置 Low 完整性标签，沙箱开关也仅存在于测试环境。

真实升级验收使用完整旧版和新包、真实 Electron/NSIS/外部助手。为避免触碰正在运行的用户应用，测试副本使用独立 exe 名称，并仅在 NSIS **测试副本**移除注册表/快捷方式写入、改用较快压缩。它验证实际文件替换、退出等待、失败回滚、重新启动及版本确认；不是用户正式安装位置或正式签名发布产物的覆盖安装证明。最终数字与截图见 [验收报告](windows-update-evidence/REPORT.md)。

回滚开发改动：独立分支撤销对应提交或继续使用原安装包。分支推送依用户明确授权；不自动合并 main、不创建 Release，不调整签名或发布审批。
