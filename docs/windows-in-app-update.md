# Windows 应用内更新

此功能由用户主动触发。发现新版本仍只显示设置入口提示，不弹窗、不下载。

在「设置 → 应用与更新」检查版本，阅读可独立滚动的更新说明，点击「下载更新」。下载显示进度、平均速度，可取消、失败后重试。SHA256 验证完成才显示「重启以更新」；选择「稍后」保留缓存，下次启动离线重新校验本地包。只显示当前阶段的主操作，手动安装版、便携包和校验和收在「手动下载与校验和」中。Pi 运行时更新仍是独立功能，可展开查看。

## 运行形态

| 形态 | 行为 |
| --- | --- |
| Windows NSIS 安装版 | 完整流程。当前 exe 的 realpath 必须匹配 HKCU 卸载记录 `InstallLocation\Pi GUI.exe`，且卸载程序存在。 |
| 便携版 / 无法确认的打包形态 | 下载并验证便携 ZIP，打开固定下载目录；退出后手动替换，不覆盖正在运行的 exe。 |
| 开发模式 / 其他平台 | 检查和手动 Release 链接，不执行自更新。 |

不得仅凭 `app.isPackaged`、exe 名字或位于 Programs 目录判断安装版。

注册表使用固定 PowerShell Registry API 和显式 UTF-8 管道读取，支持中文、全角符号及空格路径；安装助手也显式按 UTF-8 读取请求 JSON。缓存初始化失败时保留受信 IPC，显示原因并允许重试；IPC 连接失败有单独的重试入口，不再静默降为手动下载。

旧版二进制不能自动获得尚未安装的修复。受中文路径识别缺陷影响的旧安装，需要手动安装包含本修复的版本一次，此后才使用修复后的应用内更新链。当前源码改动不修改用户已安装的 v0.29.0，也不创建或发布新版。

## 权限与完整性

`server/update-check.js` 仍只负责发现；主进程通过已认证的本机 API 复用其结果。GitHub 地址、文件名、大小、版本和 SHA256 不来自 Renderer。IPC 仅暴露读取状态、下载、取消、打开便携包目录和请求安装；只接受主窗口的同源顶层 frame。安装前还会显示原生确认框。

资产必须是固定仓库 `HYJ1817/pi-gui`、精确的 `v<版本>` tag 和 `Pi-GUI-Setup-<版本>.exe`（或便携 ZIP），大小为正整数且不超过 1 GiB。下载只接受固定官方地址；每次重定向也必须是 GitHub Release 下载地址或 `release-assets.githubusercontent.com` / `objects.githubusercontent.com`。没有自定义更新源，也不转发令牌、Cookie、项目、会话或供应商数据。

优先使用公开 GitHub Release API 的 `sha256:` digest，缺失时只从相同版本的官方 `SHA256SUMS.txt` 取精确条目。安装前重新读取官方信息并比较 SHA，包括 checksum fallback，不能靠可修改的本地 manifest 建立执行信任。HTTPS/GitHub 账号是信任根；此机制不能抵御官方发布账号被接管，不替代既有签名与发布审批。

更新包位于当前用户临时目录 `pi-gui-updates`，先写 `.part`，验证成功才重命名并保存 `ready.json`。恢复缓存时重新计算文件 SHA256，过期版本不被当作可安装版本。目录 identity、文件类型和链接检查用于拒绝缓存路径替换。进程内下载单飞；外部助手还持有 OS 排他安装锁及安装包只读句柄。

## 安全退出

后端私有父子 IPC 承担维护控制，HTTP/Renderer 不能调用该通道。更新前检查：Classic 和全部 Runtime 活动、待处理审批、未应答命令及 RPC、停止屏障、认证、CLI、Pi/扩展更新、Planner/验证、候选任务收尾、托管进程、工具调度和文件变更 lease，以及未完成 HTTP 写请求。主进程还检查经典与全部 Runtime 浏览器操作/加载；活动浏览器操作拒绝退出，空闲打开页面的数量与可能丢失的未提交输入写入原生确认框。

任一项忙或无法确认时拒绝重启，提示等待，或先在对应会话安全停止。此版不提供强制终止升级。维护锁同步获取后禁止新 HTTP 写请求，关闭空闲 Runtime 并确认清理；Classic 仅关闭 stdin、等待退出，不走 `taskkill /F`。若退出无法确认，取消更新并恢复可用状态。

只读预检后显示原生确认框；确认后重新获取维护锁并检查，预检不构成退出许可。准备超时会取消迟到的维护操作并等待释放，避免后台迟到暂停后端。浏览器撤销/清理发生在后端仍可恢复的阶段。

只有维护成功才启动位于安装目录之外的助手；写 armed 标记后请求后端正常退出，并确认实际退出，再退出应用。助手必须同时证明旧主进程已退出、armed 存在且未被取消，才可安装。它预先打开旧主进程句柄并核对启动时间，避免 PID 复用；关闭该句柄后，还必须证明 exe 已能排他写打开，不能把主进程退出误当作所有文件映射均已释放。

Windows PowerShell 由固定参数的隐藏 `Start-Process` 宿主启动。真实 Electron 验证发现：直接 detached 启动可能返回 0 却未执行脚本，直接附着启动又可能随父进程退出；不能把它们当作已成功启动。启动仍以助手写入 ready 为准，助手自己的排他安装锁与旧父进程身份才是安装资格，不以引导进程的退出作为助手已结束的证明。

准备或退出失败会撤销 armed、通知助手取消，并独立释放后端维护态。标记写入/删除失败不能跳过后端恢复：此时显示「正在撤销」，拒绝关闭窗口和正常退出，等待安装助手释放排他锁。助手等待父进程时可收到取消；若标记也无法写入，等待原有 120 秒超时。若后端已退出，确认助手已结束可安装阶段后重新启动整个旧应用，重建浏览器宿主和后端，避免留下仅版本界面可用的残壳。

## 安装、恢复和重启

助手先重新计算 SHA256 并保持安装包只读句柄，再等旧应用完全退出。复制程序目录到该次临时更新目录下的 `backup`，然后使用固定参数 `/S /D=<当前安装目录>` 调用 NSIS。NSIS 静默路径遇仍运行实例返回 20，不强杀；无法覆盖文件返回 21，不出现隐藏确认框。

备份前记录整个程序目录的相对路径、类型、大小和 SHA256，复制后逐项验证，只有完整备份成功才启动 NSIS。安装非零退出或安装后 package 版本不匹配时，在同一安装锁内恢复这份清单：只移除相对备份新增、且在安装器退出后的观察中身份和内容仍一致的普通文件；新增目录按最深层优先逐个删除，操作系统拒绝删除非空目录。所有更新前已有路径均从备份恢复，末尾重新比较整个目录集合和摘要，完全匹配才记录 `rolled_back` 并启动旧版。

恢复使用 Windows 原生句柄核对最终路径、卷/文件 ID、重解析点和硬链接数量；目录句柄防止恢复中被改名，删除通过同一文件句柄执行，已有目标文件通过排他句柄核对身份和内容后写回。备份损坏、链接、路径/身份改变、额外并发变更或清单不符均返回 `recovery_required`，保留备份并停止自动启动，绝不清空安装目录。这里的“新增”以已持锁的程序目录在安装前后观察的差集为范围；安装锁协调本应用的安装助手，不是同权限第三方程序的系统级隔离边界。

备份失败且程序文件未动时，确认旧 exe 的 hash 和路径未变再重启。保持原 userData 路径和数据相关环境；项目、会话、供应商、OAuth、草稿、设置及 Runtime 数据不被迁移或清空，AppData 不在备份/替换范围；userData 与安装目录相同或位于安装目录内时拒绝安装。新进程再将实际 `app.getVersion()` 与预期目标比较，只有匹配才显示完成。

助手尽力写固定错误阶段，不写底层异常原文或用户 payload；诊断写入失败不能改变等待或回滚顺序。启动恢复分为等待、成功、失败：助手持有排他安装锁（或无法确认锁已释放）时显示等待，主进程拒绝再次下载或安装，每 500 ms 离线复查；锁释放后，只有结果为 `installed` 且实际版本匹配才显示成功，缺少结果、版本不符或错误阶段显示失败。结果确认后仅清理对应 `pending.json`，提示保留在本次应用状态，下次启动不再重复。失败 UI 保留 Release 手动安装入口。程序文件备份和结果保留在该次临时目录，便于故障恢复；系统清理临时目录后需重新下载。

若磁盘故障使备份也不能恢复，记录 `recovery_required`，需手动重装程序；用户数据保持原处。若安装程序超过十分钟仍未退出，记录 `installer_timeout` 并保持锁等待它退出，不杀安装器、不与其并发回滚。断电、系统强制结束和真实签名后的下一版公网更新仍需发布前人工验收。

## 验证

```powershell
npm run test:app-update
npm run test:app-update:electron
npm run test:app-update:installed
npm run test:app-update:helper-startup
npm run test:app-update:installed-failure -- --world=<上一项成功安装专项的 TEMP 目录> --failure=exit
npm run test:app-update:installed-failure -- --world=<同一 TEMP 目录> --failure=version
npm run test:app-update:windows -- --previous-zip=<官方 v0.29.0 便携 ZIP 绝对路径>
node tests/app-update-windows-faults.cjs
```

默认专项完全离线，已纳入 `npm test` 的唯一测试链。Windows 验收不下载资产；输入 ZIP 必须匹配脚本内记录的官方 SHA256。所有写用例使用 `os.tmpdir()` 夹具；受限 Windows 测试仅给新夹具设置 Low 完整性标签，沙箱开关也仅存在于测试环境。

设置 `PI_UPDATE_E2E_CONTINUE_FAILURE=1` 可在成功安装专项后按顺序执行两种失败回滚，输出目录分别为 `failure-exit` 和 `failure-version`。真实故障 NSIS 实际写入旧版不存在的文件和嵌套目录，并保留执行凭据；回滚后比较完整程序目录清单和每个文件的 SHA256。默认 canonical 中的 `tests/app-update-rollback.cjs` 使用真实 Win32 句柄与 TEMP 文件覆盖嵌套恢复、备份损坏、junction、hardlink、身份替换及安装后外部新增的拒绝恢复行为，不依赖 NSIS 下载。

`test:app-update:installed` 是补充专项：需要现有离线 Electron ZIP、NSIS 和先重建的 `dist-app`，从 TEMP 源码副本分别构建当前版与下一补丁测试版，实际运行主进程、preload、后端、下载器、助手和 NSIS。测试版不修改仓库版本或正式 Release。默认等待操作者确认真实原生窗口；无人值守可显式设置 `PI_UPDATE_E2E_AUTOMATED_CONFIRM=1`，报告会记录确认应答为测试夹具，不能声称完成原生点击验收。设置 `APP_UPDATE_EVIDENCE` 可指定证据输出目录。测试安装器副本使用独立 exe 身份、较快压缩并去掉全局注册表/快捷方式写入；安装位置识别和公开 Release 传输是隔离夹具，不能冒充正式发布包原位置升级证明。`test:app-update:helper-startup` 独立验证生产启动器执行脚本并跨真实 Electron 父进程退出继续工作，路径包含中文、空格和单引号。当前结果见 [2026-10-27 验收](in-app-update-20261027-acceptance.md)。

真实升级验收使用完整旧版和新包、真实 Electron/NSIS/外部助手。为避免触碰正在运行的用户应用，测试副本使用独立 exe 名称，并仅在 NSIS **测试副本**移除注册表/快捷方式写入、改用较快压缩。它验证实际文件替换、退出等待、失败回滚、重新启动及版本确认；不是用户正式安装位置或正式签名发布产物的覆盖安装证明。最终数字、截图与未验证边界见 [验收报告](in-app-update-20261027-acceptance.md)。

回滚开发改动：独立分支撤销对应提交或继续使用原安装包。分支推送依用户明确授权；不自动合并 main、不创建 Release，不调整签名或发布审批。
