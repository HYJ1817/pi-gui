# 人工审阅（P8）

> 这一篇讲**产品语义**：界面上那个人工验收流程是怎么想的、边界在哪。
> 数据契约（字段形状、归一化规则、并发写者的字段所有权）见
> [workflows.md](workflows.md) 第五节与第六节 —— 这里不重抄一遍。

## 一、为什么「执行成功」不等于「人工验收」

这是整个 P8 的出发点：

```
执行成功  ≠  人工验收
人工验收  ≠  自动验证
历史验收  ≠  当前工作区仍然保持原样
```

Agent 报 `success`、退出码 0、摘要里写着 "tests passed" —— 这些都只是
**它自己的说法**。所以：

- **「验证结果」这一行不是 Agent 的说法，而是 Pi GUI 自己跑出来的东西。**
  从 P9 起，你可以对某一次已经结束的 Attempt 点「运行验证」，由 Pi GUI 执行
  那次 Attempt 当初冻结的 `verificationSnapshot.command`，把真实的退出码、
  耗时和输出摘要记在那条 Attempt 上。**没跑过**才显示「尚未独立确认」；
  跑过之后显示的是机器实际跑出来的结果（见第六节）。
- 但界面**仍然没有**「已验证」这个**审阅**状态，也没有「标记为已验证」的入口 ——
  验证通过不等于你验收通过，那仍然要你自己点。
- **Agent 摘要不会自动填进审阅说明**，更不会把「摘要里写着 tests passed」
  变成「已接受」。摘要显示在它自己的位置上，是**被审阅的材料**，不是结论。
- 审阅状态与执行状态**同时存在、各答一个问题**：

| | 谁写 | 取值 | 回答 |
|---|---|---|---|
| 执行状态 | Scheduler | `success` / `failed` / `cancelled` / `interrupted` | 机器跑出来什么 |
| 独立验证 | **Verifier** | `running` / `passed` / `failed` / `interrupted` | Pi GUI 自己跑出来什么 |
| 人工审阅 | 人 | `pending` / `accepted` / `needs_changes` | 我认不认这个结果 |

所以 `success + needs_changes` 是合法的，「跑通了，但我不满意」。

## 二、只有三个审阅状态

```
待审阅   pending          ○
已接受   accepted         ✓
需修改   needs_changes    ↻
```

**刻意没有** `approved` / `verified` / `rejected` / `stale` / `obsolete` /
`superseded`。状态一多，用户就得先学一套词汇才能表达「我认不认」；
而其中好几个（`stale` / `superseded`）还想表达「这条判断过时了」——
那是**顺序**能表达的事，不需要再加一个状态。

界面上的状态**一律带文字**，颜色只是辅助 —— 只画绿点红点，色觉障碍用户
读不出状态。

## 三、审阅挂在「某一次 Attempt」上，不挂在任务上

一个任务可能跑过很多次。**每一次执行结果都是独立的**，所以审阅也挂在
attempt 上：

- 每次重试产生**新的** attempt，新的 attempt 从「待审阅」开始 ——
  上一次判过 `accepted` 是人对**那一次**结果的判断，不继承。
- 旧的 attempt 卡片、它的审阅状态、说明、时间**原样留着**，重试不会隐藏它们。
- 旧的那条 `accepted` 的含义**不变**：它始终只表示「你曾接受那次尝试的结果」，
  **不表示它仍是当前最新结果**。当前/最新由 attempt 顺序表达 ——
  所以界面上**不会**把旧的 accepted 改写成「已过期 / 旧版」。

**哪次执行允许「接受」：**只有**执行成功**的 attempt。失败 / 取消 / 被中断的
attempt 只能标「需修改」——「接受一个失败的结果」没有意义。这条规则后端
（`canAcceptAttempt`）和前端各判一次：前端只是不让你点了白点一次，
**即使绕过前端，后端也会拒绝**。

**正在执行的那一次不给审阅操作。** 它在历史里还不存在（attempt 号在开始时
涨上去，记录是结束时才写的），所以界面上显式占位一行并说明「任务仍在执行，
完成后可进行人工审阅」。更早的 attempt 不受影响，照样可以审阅。

## 四、验证要求是「当时」的，不是「现在」的

每条 attempt 带一个 `verificationSnapshot`：**这次执行开始时**任务要求的
verification 是什么。在开始时冻结，所以之后改 `task.verification` 不会篡改历史。

- 有快照 → 直接显示（`command` 或 `description`，只认这两个键）。
- 没有快照（P8-A 之前的老 attempt，或当时没写要求）→ 如实说
  「该次执行没有保存历史验证要求」。这时如果**当前任务**有要求，会另起一行
  标出来，前缀必须写「**当前任务**验证要求」—— 否则用户会以为那是当时的要求。

## 四之二、独立验证结果（P9）

上一节说的「验证要求」是**要求什么**；这一节说的是 Pi GUI **真的跑了什么**。
它们是同一条 attempt 上的两个字段，**永远不合成一个**：

```
verificationSnapshot   这次 Attempt 开始时要求验证什么（冻结的历史要求）
verificationResult     Pi GUI 后来真的执行过什么、结果如何（机器证据）
```

### 怎么触发

在 attempt 卡片里点「运行验证」。跑的是**那条 attempt 当初冻结的命令** ——
不是当前 `task.verification`（那可能早改过了），更不是**由 description 猜**出来的
一条命令。

| 这条 attempt 有 | 能不能跑 |
|---|---|
| `verificationSnapshot.command` | 可以，按钮就是它 |
| 只有 `verificationSnapshot.description` | **不跑**，只显示描述 |
| 没有快照（P9 之前的老记录） | **不跑** —— 拿当前任务的要求顶上去等于伪造历史 |

### 四种状态

| 状态 | 意思 | 界面措辞 |
|---|---|---|
| `running` | 命令正在跑（**只有本进程在跑才算**，见下） | 正在验证… ＋「停止验证」 |
| `passed` | 退出码 0 | 通过 |
| `failed` | 非 0 退出 / 超时 / 命令起不来 | 失败 ＋ 退出码、耗时、输出摘要 |
| `interrupted` | 你按了停止，或应用退出时它还在跑 | 已中断 |

**停下来的那次是 `interrupted` 而不是 `failed`** —— 你没跑完，不是它错了
（与「取消 ≠ 失败」同一条规矩）。

`running` 是**会落盘**的状态，所以崩了之后不会永远停在「正在验证…」：
进程启动时（且只在启动时）会把落盘的 `running` 收成 `interrupted`，
与 task 的 `running` 是同一套处理。

### 它只写它自己那一格

验证**绝不**：改 `task.status`、改 `review.status`、触发 Retry、自动 accepted。

所以下面两种组合都合法，界面上也分得很清楚：

```
执行状态：成功      独立验证：失败      人工审阅：待审阅
执行状态：成功      独立验证：通过      人工审阅：需修改
```

「验证通过 + 需修改」不是矛盾 —— 通过的是那条命令，不满意的是那次改动。

### 什么时候不让跑

**同一个 Pi GUI workspace 同一时间只允许一个「会实际执行工作区命令」的主体。**

```
Scheduler 在跑  →  任何验证都起不来（包括**同一个 workspace 的另一个计划**）
验证在跑        →  起不了计划、起不了另一条验证、不能 Retry
                   不能改计划结构（PUT）、不能删计划、不能切项目
```

理由很直接：验证命令和 coding agent 会同时改同一个工作区、抢 `index.lock`、
把测试结果搅成一团，出了问题说不清是谁的。

判定是**全局**的，不是「只比当前这个 Plan」—— 只比当前 Plan 的话，
「Plan A 在跑，去验证 Plan B」就能穿过去（那是同一个工作区）。

拒绝时给的是稳定 `code`，而且**分得开**：

| code | 意思 |
|---|---|
| `already-running` | 你点的**就是**正在跑的那一条 |
| `verification-active` | **另外**一条正在跑（提示里会点名是哪一条） |
| `plan-active` | 有计划正在执行（任意一个计划） |

**Review 保存与清除不受影响** —— 它和验证之间已经有字段所有权与并发写盘保护。
纯读取（看计划 / attempt / 审阅 / diff / 会话 / 验证输出）当然也不受影响，
停止验证更是必须允许。

### 老 attempt 用的是哪个目录：fallback 要如实说

验证在哪跑，优先用**那次 attempt 开始时冻结的**工作目录
（`workingDirectorySnapshot`，与 `verificationSnapshot` 同时刻冻结）——
因为 `task.workingDirectory` 是可编辑的：Attempt 1 当初在 `packages/a` 跑，
你把 task 改成 `packages/b` 之后再验证它，在 `packages/b` 里跑出来的结果
**不再对应那次执行**。

P9 收口之前产生的 attempt 没有这个字段，只能退到当前值，但结果里会记：

```
workingDirectory:        packages/legacy
workingDirectorySource:  current-task-fallback
```

界面上会**明确写出来**：「这次执行没有记录当时的工作目录，上面显示的是当前任务的
目录 —— 证据强度低于冻结记录」。冻结来源（`attempt-snapshot`）则不提醒。

**两件不能让的事**：

- 快照**非法**（绝对路径、`../` 逃逸、经 junction 指到项目外）→ 直接 `invalid-cwd`
  拒绝。**不退到 fallback** —— 那会静默跑到别的地方去。
- fallback 的目录也要过同一套 `lib/safe-path.js` 校验；不存在同样 `invalid-cwd`。

### 输出有上限

命令输出可能几百 KB，而计划是个**整份读写**的 JSON 文件。所以只留**末尾**
2000 字符（失败原因几乎总在最后几行），超出时明确标「输出已截断」——
悄悄只给末尾会让人以为「输出就这么点」。

### 重新运行

可以反复跑同一个 Attempt，第一阶段**只保存最新一次**结果（不做验证历史时间线）。
数据形状留了余地：`verificationResult` 是 attempt 上的一个字段，
将来要变成数组是 additive 的改动。

## 五、两种 Diff：当前工作区 vs 那次执行（P10 起）

attempt 卡片上**并排两个入口**，措辞刻意分开，不能混：

| 入口 | 说的是什么 | 会不会变 |
|---|---|---|
| 查看**当前** Diff | 工作区**此刻**相对 Git 基线是什么样 | 随工作区漂移 |
| 查看**本次** Diff | 这次执行**执行前 → 执行后**观察到的工作区变化 | 一旦写下不再变 |

P7/P8 **从来没有保存过历史 diff**，只存了 `filesChanged`（一份文件名清单），所以那时
attempt 里那个入口给的只能是**当前工作区**的差异。P10 起，每次执行会在执行前后各把
工作区写成一棵 git tree（**临时 index，不碰用户真实的 `.git/index`**），两棵树的差集
就是这份冻结证据，随 attempt 一起落盘。所以「本次 Diff」**不再依赖现在的文件内容** ——
之后工作区怎么改、Retry 多少次、甚至变回 clean，它一个字节都不动。

⚠️ **仍然不说「Agent 改的」。** 执行期间用户、编辑器、formatter、watcher、构建脚本都
可能动过文件，这份证据说的是「这段时间里工作区发生了什么」，不是变化的来源。
基线也刻意不是 `HEAD`（那会把用户在执行开始前就已经改好的东西算进来），
而是**执行前那一刻的工作区**。细节见 [workflows.md](workflows.md) §二之二。

配套的如实说明：

- **之后工作区又改了**：历史证据不变；只有「当前 Diff」那个入口反映现在。
- **文件现在已经 clean 了**：「当前 Diff」那边说「当前工作区已无该文件的未提交差异」，
  历史证据照常显示（那是当时的事实）。**两边都不隐藏。**
- **采不到 / 采不全**：历史证据标 `unavailable` / `partial` 并写明原因；`filesChanged`
  那边标「执行期间文件变化未完整采集」。这时候**不会**说「没有文件变化」——
  那是把「没采集到」说成「确定没有」。
- **更早版本产生的 attempt**：根本没有这个字段，界面如实说「这次执行没有变更证据
  （更早版本没有采集）」，**不假装有 Diff**。

采集失败**不影响任务结论**：证据是附加物，不是任务成功的前提。

## 六、Retry 与旧的 accepted

重试的完整语义见 [planner.md](planner.md) 与 [workflows.md](workflows.md)。
与审阅有关的只有三条：

1. 重试**不删**旧的审阅，也不改它。
2. 重试后新 attempt 的审阅从 `pending` 起。
3. **计划还在执行时不能重试**（`plan-active`）—— 等计划结束或先停止整个计划。

## 七、审阅不驱动任何执行

保存审阅**只写审阅**：

```
不触发重试   不暂停计划   不动 DAG   不改 task.status   不调 Agent   不碰 Git
```

具体地说：标了「需修改」**不会**自动重试；标了「已接受」**不会**自动 commit、
也不会锁定任务（以后照样能改判断、清除、主动重试）。

Plan 顶部那个汇总也**只是信息展示**：`needs_changes` 再多也不会暂停计划、
不会禁止下游、不会改 DAG。

它按**每个任务的最新一次 attempt** 归类：

```
执行结果      成功 3 · 失败 1 · 尚无结果 1
成功结果审阅  已接受 1 · 需修改 1 · 待审阅 1
```

- 只看最新一次：`Attempt 1 成功且被接受、Attempt 2 失败` 的任务算**失败**，
  不会因为历史曾成功而多算一个「已接受」。历史那条 `accepted` 仍然显示在
  Attempt 1 卡片里。
- 失败 / 取消 / 被中断的最新结果**不进「待审阅」的分母** —— 那不是一个
  待验收的产物。
- 没有 attempt 的任务算「尚无结果」，不算「待审阅」。

界面上没有审批网关、没有「通过率」仪表盘、没有巨卡片墙 —— 就两行字。

## 八、冲突与 revision

每条审阅记录带一个单调递增的 `revision`。保存时前端**带上它读到的那一版**，
对不上就是别的窗口改过了，后端回 `code: 'review-conflict'`。

前端在冲突时：

- 显示「这条审阅已经在其他窗口被修改」+「重新加载」；
- **本地输入原样保留**（写了一半的说明不会因为一次冲突就没了）；
- **不自动重试、不 last-write-wins、不自动合并说明** ——
  两条人工判断之间没有「合并」这回事，猜一个结果等于替用户做决定。

点「重新加载」是**用户明确的覆盖动作**：重新拉一次计划详情、丢掉本地草稿。

冲突识别**只看 body 里的 `code`，不看 HTTP 状态码**：前端 HTTP 层
（`public/api.js`）只做 `await r.json()`，从不读 `res.status`。

## 九、当前限制

明确记下，不含糊过去：

- **独立验证要你手动触发一次。** Pi GUI 会跑命令，但**不会自己判断该不该跑** ——
  没有「保存后自动验证」、没有「计划跑完自动验证」、没有验证历史的**时间线**
  （只保存最新一次）。而且它跑的是**冻结的那条命令**，不是它理解出来的验证意图。
- **没有 AI 裁判。** 验证通过与否是退出码说了算，没有人（也没有模型）替你解读输出。
- **没有历史 diff 的「重算」。** P10 起历史 diff 是**执行时冻结**下来的
  （`changeEvidence`），不会在打开时按当前工作区重算 —— 见第五节。
- **没有 AI 裁判 / 自动审阅 / 自动 Retry / Review Gate / 自动 commit。**
  审阅是人的动作，不驱动执行。
- **没有多人审批、没有云端协作。** 这一版只有一个本地界面，
  revision 冲突保护是为了「同一个人开了两个窗口」，不是为协作设计的。
- **审阅说明不支持 Markdown**，一律按纯文本渲染。
- **说明上限 1000 字**，前端 `maxlength` + 后端校验，后端是最终权威。
- **项目切换后，未保存的 Review 草稿会丢弃。** 草稿（连同「正在保存 / 正在清除」
  的标记、文件列表的展开状态）都属于**旧 workspace**，所以 `workspaceGeneration`
  一变就整体作废；在途的保存响应回来时也不再更新界面，旧面板会被收成
  「项目已切换，请重新打开 Planner」。这是刻意的：不是「保留跨项目草稿」，
  而是「项目切换 = 草稿生命周期结束」。草稿只活在内存里，不写
  localStorage / sessionStorage / plan 文件。
- 冲突保护面向「同一个人开了两个窗口」，不是多人协作。
