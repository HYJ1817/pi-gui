# Z4-5 大图事务限制与原子布局设计与阻断分析

本报告由 Codex 于 2026-10-26 编写，针对 Z4-5 任务 E 中“超过 50 个节点自动布局的大图事务限制”开展深入协议审计、架构评估与阻断分析。

---

## 一、现状与边界审计

### 1. 现有协议常量与约束 (`lib/collab-doc.js`)
在当前生产协同文档模型中，系统通过严格参数限制保障确定性与防 DoS：
- `LIMITS.maxNodes = 200`：图最大节点容量。
- `LIMITS.maxEdges = 400`：图最大连线容量。
- `LIMITS.opsPerProposalMax = 50`：单次受控提案/批次操作最大上限。
- `LIMITS.journalMax = 500`：文档操作幂等日志（`appliedOps`）最大容量。
- `OP_TYPES`：封闭的操作类型集合，仅允许 6 种微操作：
  `node.add`, `node.update`, `node.remove`, `edge.add`, `edge.update`, `edge.remove`。

### 2. Z4-4B 现状
在 Z4-4B 中，当自动布局计算发现需要移动的节点数大于 50 时，`createLayoutPreview` 将状态标记为 `over-limit`，UI 工具条明确提示用户：
> “需要移动 N 个节点，超过单批 50 条操作上限；为避免部分静默保存，本轮不提供自动分批，请手动分区整理或等待大图事务方案。”

同时禁用“确认应用布局”按钮，实现 fail-closed，保证绝无部分写入。

---

## 二、候选技术方案评估

为了支持超过 50 个节点的原子布局，理论上有以下三种演进路线：

### 方案 A：提高全局批次操作上限 (`opsPerProposalMax` 50 → 200)
- **机制**：直接将 `LIMITS.opsPerProposalMax` 提升至 200 或 600（满足最多 200 节点移动）。
- **风险与阻断**：
  1. **幂等日志挤压**：当前 `journalMax = 500`。若单次提交 200 条微操作，单批即占满 40% 的日志空间；两次连续操作即冲刷掉早期历史，导致并发客户端的轻量重放判定失效。
  2. **Agent 提案爆炸**：`opsPerProposalMax` 同时约束 Agent 修改建议。若放宽到 200，LLM 可能会产出动辄上百条操作的巨型 Proposal，导致 `describeBatch` 人类可读差异生成、HTTP 传输及 SSE 通道出现明显的卡顿甚至体积超限（`LIMITS.serializedMaxBytes = 2MB`）。
  3. **计算复杂度上升**：`applyOperations` 在副本上逐条校验和模拟。200 条操作排序与二次指纹计算会大幅增加主线程阻塞时间。

### 方案 B：分批串行提交 (客户端或服务端自动拆分批次)
- **机制**：若有 80 个节点需要移动，自动拆分为 `Batch 1 (50 ops)` 和 `Batch 2 (30 ops)` 顺序提交。
- **风险与阻断**：
  1. **破坏事务原子性**：违反任务硬约束：“不允许通过自动发送多个 50 条操作批次绕过限制”。若 Batch 1 成功但 Batch 2 因网络中断、进程崩溃或 CAS 版本冲突失败，图将停留在半布局状态，坐标撕裂。
  2. **破坏单步撤销**：用户点击一次“确认布局”，在撤销时必须撤销两次才能还原，违背用户预期。
  3. **CAS 冲突脆弱**：Batch 1 提交后版本号+1，若并发有用户其他操作，Batch 2 必报 CAS 冲突，导致部分应用。

### 方案 C：引入专用原子复合操作类型 (`graph.layout` 或 `node.bulk_update`)
- **机制**：在 `OP_TYPES` 中扩展新操作类型，例如 `node.bulk_update` 或 `graph.layout`，其 `params` 包含 `{ positions: [{ id, x, y }] }`。
- **理论优势**：
  1. 单个 `opId`，仅消耗 1 条 journal 条目。
  2. 一次 CAS 校验，一次 `revision + 1`。
  3. 逆操作计算简洁：只需将原各节点的坐标记录在逆操作的 `positions` 中，单次 undo 即可完全还原。
- **阻断项与未满足的前提**：
  1. **破坏六类封闭操作协议**：引入第 7 类操作类型将影响：
     - `validateOperationSchema` 与 `validateAgainstState`。
     - `computeInverse` 与 `inverseOf`。
     - `describeBatch` / `describeOperation`：前端审查与可读差异。
     - 现有持久化文档的旧版本兼容性（升级降级风险）。
  2. **权限与注入边界扩展**：Agent proposal 若能直接调用 `node.bulk_update`，必须防止 Agent 伪造越界坐标或注入非法节点 ID。
  3. **变更风险与稳定性**：该改动涉及底层 `collab-doc.js` 核心协议，属于高风险底层协议重构。在当前 Z4-5 聚焦于前端编辑交互的迭代中强行引入，违背“渐进交付”与“不为大图取消 50 条限制而妥协稳定性”的指导思想。

---

## 三、当前结论与决策

依据任务指导规则：
> “只有在能够同时证明一次用户确认对应一个原子提交、失败不改变原文档字节、无部分应用、CAS 冲突 fail closed、Undo/Redo 正确等条件时，才允许实现生产功能。如果无法满足，不要强行开发。保留当前 over-limit 行为，产出设计与阻断分析。”

**决策结论**：
1. **本轮维持当前 `over-limit` 明确拦截行为**：不放宽 50 条限制，不进行分批伪应用，完全杜绝部分静默保存与历史错乱。
2. **候选方案 C 作为下一代协同架构 (Z5) 规划**：在未来引入复合操作协议标准时，通过严格的 Schema 扩展、完整的迁移脚本以及全覆盖的故障注入套件后，再正式上线生产。
