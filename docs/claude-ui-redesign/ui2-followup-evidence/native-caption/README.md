# Windows native caption follow-up

Run `node tests/ui2-native-caption.cjs` from the integration checkout.

Final run: **42/42 checks, exit 0, 35.254 seconds**. Electron 44.4.3 / Chromium 152.0.7977.130. There are **17 native window images and 17 caption crops**. `report.json` records every check, native ownership/desktop/visibility facts, renderer rectangles, capture method, native glyph counts and sampled titlebar pixels.

Coverage: initial dark; light then dark theme changes; app zoom 80/100/125/150 percent in both themes; maximized and restored in both themes; actual production Changes and Browser panes in both themes. Browser uses its production controller/agent and an empty address; no external site is loaded. The independently rendered Browser viewport has not navigated and retains its existing blank dark surface even in the light-theme scene; this acceptance checks the header/native-control seam and does not claim that Browser page content follows the app theme. Right-pane checks require real nonzero bounds, hidden=false and the actual changes/browser surface. For example, both panes at zoom 1 have CSS bounds x=780, y=0, width=420, height=902. Screenshots were inspected to confirm the panels are actually rendered rather than merely named in the output.

The final four matrix guards require exactly all 17 unique expected scene names, every scene available with an allowed owned-window capture method, nonempty stage and rail pixel samples plus a pane sample whenever visible, and all four pane names matching their precise changes/browser surfaces. A missing or unavailable scene therefore fails the run. `intermediate-38-report.json` preserves the successful run before these completeness guards were added.

Each scene checks real native minimize, maximize/restore and close glyph pixels against the production symbol palette, with at least four glyph pixels per control and at least 300 background pixels in each sampled control patch. Typical restored-window counts are close=56, maximize=70, minimize=30; the restore glyph in a maximized window has 78 matching pixels. Separate checks compare native image pixels with the production stage, project rail and visible right-pane titlebar colors. Dark is RGB 17/17/17 and light is 251/251/249. No screenshot is produced with capturePage.

Twelve full images use GDI CopyFromScreen of the owned client rectangle inset by four physical pixels. The fixture is topmost and shown without activation; foreground ownership is recorded, rather than assumed. Before and after copying, the helper checks the target PID, visible/not-cloaked state, interactive desktop, external visible/non-cloaked windows earlier in Z-order whose rectangles intersect the capture area, and a 16-pixel WindowFromPoint grid across the capture rectangle. The successful normal-window copies each check 9,408 grid points with zero mismatches and zero external intersections. The image is saved only if the after-copy ownership checks also pass. No external window content or desktop-wide screenshot is captured.

Five scenes fail that conservative screen-copy guard and fall back to PrintWindow against the exact owned HWND: light-maximized, light-restored, dark-zoom-1, dark-maximized and dark-restored. These still pass native glyph/theme pixel checks; they are explicitly identified in the report and are not presented as CopyFromScreen evidence. The two maximized windows have 96 rejected grid samples, so no broader screen copy is attempted. Both Changes and Browser panels in both themes use verified CopyFromScreen.

The hidden-launch negative reports explain the earlier black-image result. `hidden-launch-report.json` records a hidden own HWND, a failed own-window foreground attempt and uniform black PrintWindow pixels. `showwindow-first-call-report.json` records that windowsHide=false made visibleBefore=true, but a first ShowWindow call from the hidden PowerShell helper hid the target again. The final launcher uses windowsHide=false, and the helper does not issue ShowWindow for an already-visible fixture. Those negative reports retain their original facts; their original dark-initial PNG was superseded by the final successful capture.

A second limitation was caught by visual inspection: a nonuniform PrintWindow image can contain freshly drawn native controls over an older Chromium surface. Making only the owned fixture topmost and explicitly invalidating its web contents caused current theme/pane rendering to appear; the final titlebar pixel checks and verified screen copies prevent accepting stale white content for a dark pane. No product change was required.

Security and scope: contextIsolation=true, nodeIntegration=false, sandbox=true, no --no-sandbox, no GPU-disabling flags, no OS security/theme/DPI changes. Actual display scale is 1.5; app zoom coverage does not establish OS DPI-switch coverage. The fixture restores topmost status and destroys its own window, stops its own Browser agent and offline port-0 harness, and removes temporary userData. It does not manipulate user applications or real Pi/session data.
