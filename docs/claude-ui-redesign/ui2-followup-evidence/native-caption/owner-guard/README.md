# Current native caption acceptance with ownership guards

Run `node tests/ui2-native-caption.cjs` from the integration checkout. The test now writes to this `owner-guard/` directory. The parent directory's 42/42 run, screenshots, negative-launch reports and manifest are historical evidence and have not been changed by this follow-up.

Final result: **45/45 checks, exit 0, 37.089 seconds**, with **17 native window images and 17 caption crops**. `report.json` is the current structured report; `run.log` contains the actual process output, including Electron child exit 0. The exact screenshot manifest filename is **image-manifest.json**, located in this directory; it records byte counts and SHA-256 for all 34 PNG files.

The original 42 checks remain: the complete unique 17-scene matrix, availability and allowed capture methods, native three-control glyph/theme pixels, nonempty stage/rail/pane titlebar pixels, and the four real Changes/Browser pane surfaces. Three checks were added: two mismatched-owner negative controls and a guard requiring all 17 positive captures to have successful ownership checks at their API/save boundaries.

Both negative controls target a second window created by this same Electron test, never a user window. That window is alive and visible: the report records IsWindow=true, visible=true, actual PID 33932 and deliberately mismatched expected PID 33933. One control considers the screen-copy path and its fallback; the other explicitly disables screen-copy to exercise fallback selection. In both cases CopyFromScreen calls=0, PrintWindow calls=0, saved=false, and imageExists=false. Their named rejection reasons distinguish the disabled path from the failed HWND/PID guard. No negative-control PNG exists. `intermediate-hidden-negative-report.json` retains the earlier successful 45-check run whose second test window was hidden; the final visible-window controls remove that extra reason for rejecting capture.

The capture helper now checks IsWindow and GetWindowThreadProcessId==expectedPid immediately before either capture API. Screen copy additionally requires visible/not-cloaked state, input/thread desktop compatibility, zero external visible/non-cloaked Z-order intersections and a 16-pixel WindowFromPoint grid wholly attributable to the target root. After copying it rechecks valid HWND, PID, visible/not-cloaked state, Z-order intersections and the hit grid; immediately before saving it again checks valid HWND, PID and visible/not-cloaked state. The report records copyOwnerBefore, copyOwnerAfter, copyVisibleAfter and copyOwnerBeforeSave. PrintWindow fallback checks valid HWND/PID before the call, after the call and again before saving, recorded as printOwnerBefore, printOwnerAfter and printOwnerBeforeSave. A failed ownership check prevents the API call or saving, rather than capturing first and rejecting afterward.

Desktop name/window station compatibility is checked before capture only. This run does **not** claim that desktop identity is rechecked after capture. The parent README's older broad description of before/after desktop/PID checks should not be used as evidence for the earlier helper; the current source and the explicit fields above define this follow-up's actual checks.

Twelve positive scenes use CopyFromScreen of only the owned client area inset by four physical pixels, with 9,408 successful grid checks before and after and no external intersection. Five scenes conservatively refuse screen-copy and use exact-HWND PrintWindow: light-maximized, light-restored, dark-zoom-1, dark-maximized and dark-restored. Every one still passes native glyph and current titlebar palette checks. The four actual Changes/Browser panes in dark/light all use verified CopyFromScreen. Browser remains an independently rendered, unnavigated empty viewport; this evidence validates its top header/native-control seam and does not claim that its content becomes light with the app.

Security claims apply specifically to this new native-caption fixture: contextIsolation=true, nodeIntegration=false, sandbox=true, no --no-sandbox and no GPU-disabling flags. These claims do not describe the older theme-electron launcher. This fixture changes only its own window, uses temporary userData and an offline port-0 harness, and destroys its own Browser controller/agent and windows afterward. It neither changes OS security/theme/DPI settings nor operates user programs. The measured display scale is 1.5; app zoom coverage is not OS DPI-switch acceptance.
