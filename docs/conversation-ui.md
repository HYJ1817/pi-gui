# P14-B Conversation Visual System

Conversation 使用工作区内居中的阅读列。PI-Desktop 阶段 D 将内容带统一为既有 `--ds-composer-width`（760px），线程在带内保留 32px 水平内距；空间不足时收窄边距并占满剩余宽度。消息、代码块、工具摘要和附件都不能让页面横向滚动。流底部按 Composer 实测高度预留并渐隐，Composer 的结构与行为见 [composer-ui.md](composer-ui.md)。

## 消息层级

- **User**：右对齐、内容自适应的柔和灰色 Bubble，最大为阅读列的 82% 与 600px 中较小值；18px 圆角（右下角 8px）、10/15px 内距。短消息不铺满，长路径和 URL 在 Bubble 内换行；换行、行内代码与附件仍按原消息内容展示。视觉隐藏「你」标签，DOM 仍保留身份信息。用户消息的复制栏在 hover、键盘 focus 或触屏显示，复制原始文本；失败可见且可重试，不修改会话。历史用户消息与 Assistant 回复的编辑 / 重新生成入口见下节。
- **Assistant**：背景透明的开放正文，保留现有 Markdown 的段落、标题、列表、代码、引用、表格和链接语义。角色身份留在 DOM（`aria-label="助手"` 与 `data-role`），视觉上不再在每条回复前重复「Pi」；复制正文时也不会混入角色名。每个 User Turn 与下一个 Turn 的间距由 `--turn-gap` 控制；Assistant 内段落沿用 Markdown 间距。
- **状态反馈**：处理中、失败、空回复和中断继续走原有状态路径；正文优先，状态文字和 metadata 次之。没有真实功能的消息操作按钮不会出现。

## 历史消息编辑与重新生成

历史用户消息与每个 Turn 的 Assistant 回复在既有 action bar 里提供「编辑并重新发送」「重新生成」；入口复用现有 icon / tooltip / hover+focus 显现，不新增按钮系统。它们不是前端删除：后端先核对目标用户消息的稳定 entryId、当前 leaf 与原生 sessionId，再通过 Pi 的公开树导航（`ctx.navigateTree(targetId, { summarize: false })`）把活动 leaf 移到目标消息之前，随后在同一会话里发一次普通 `prompt`。原生 sessionId、会话文件、conversationId、项目 / 工作区、侧栏条目、创建时间与标题保持不变；不创建新会话、不 fork、不改写 JSONL、不改 Pi。

- 目标投影只认 Pi 的 `get_entries` + `get_messages`：前端只传可见 userIndex 与期望身份，后端在提交时重新核对 entryId / leafId / sessionId / bridge 代次。过期或跨会话请求拒绝，不做 A→B 写入。
- 只有目标会话空闲（非 streaming / compacting / queued / stopping）才允许提交；不自动停止 Agent，其他正在运行的会话不阻塞本会话编辑。
- 被替换的后续历史确实含工具 / 文件动作时，编辑器显示「重新发送会替换后续对话，之前已经执行的文件修改和命令操作不会自动撤销。」；不自动回滚文件、git 或终端，也不重放旧工具。
- 文本、Markdown、代码块与图片按原内容保留；不支持的附件类型在导航前拒绝，不退化成纯文本或旧本地路径。编辑文本若以已注册命令开头会被拒绝，避免被当成命令分发。
- 提交前失败会导航回原 leaf（旧 leaf 是用户消息或 `custom_message` 时先追加内部 guard entry）；提交已被 Pi 接受后保留新路径并走正常生成失败流程。应答丢失用 requestId 查询事务状态，不盲目重试。
- 刷新、切换会话和重启都从 Pi 原生活动路径恢复；渲染器只做乐观裁剪，不持久化第二份历史。完整实现与验收证据见 [message-edit-resend-acceptance.md](message-edit-resend-acceptance.md)。

## Thinking 与 Tool Timeline

Thinking 默认折叠，摘要行用脑图标 + 真实文本的首行预览（单行截断），不再把「思考过程」和字数当作主视觉；生成中 / 已完成 / 已中断 / 已截断等真实状态仍保留在可访问文本中。按钮用 `aria-expanded` / `aria-controls` 指向保留在 DOM 的内容；Enter、Space 可操作。流式 `thinking_end` 不覆盖用户手动展开状态，`message_end` 复用原节点，避免结束时整条消息被替换。历史重建也用同一个 Thinking 构造函数，默认折叠；状态不写入会话文件。

Tool Timeline 仍以一条 Assistant 消息中的连续 tool calls 为组。实时事件和历史结果都转成既有 `ToolEntry`，共用 `tool-view.js`；只调整行、状态文字、图标与详情按钮。运行中、成功、失败和未完成都有文字与形状，不只靠颜色。没有结构化区分的取消或中断结果继续如实标「未完成」，不推断状态或退出码。已有详情在当前行下方展开；未知工具、孤儿结果和无结果的降级规则不变。两项以上时组头写「工具调用 · N 次」；状态汇总（运行中 / 失败 / 未完成…）保留真实状态，折叠时错误仍然可见。被工作记录接管后，原生组头在视觉上让位给动作摘要，原生计数与状态仍保留在 DOM 和无障碍文本中。单条调用不摆冗余组头。

### 工作记录（连续过程展示）

`public/conversation-work-log.js` 把**连续**的思考、工具组和中间进展正文合成一条「工作记录」披露：User 消息、Plan、最终回答、错误和轮次终态都是硬边界，始终留在记录之外。它只做展示归并，不创建运行、尝试、所有者或成功证据，也不包裹 P5 的 `[data-execution-turn]`；原生节点、顺序、锚点、编辑目标和事件处理器都可恢复。

- 记录头的主标题是**轮次耗时 / 状态折叠入口**：正常结束显示「执行了 3 分 27 秒」，运行中「执行中 · 已运行 5 秒」，用户停止「你在 8 秒后停止」，失败 / 中断 / 未完成附「用时」。补充输入后的段落显示「继续执行了 …」；没有可信时间证据时退回「工作记录」/「继续执行」，不伪造 0 秒。摘要、计数与状态是活动摘要，不宣称任务成功。
- 记录头同时显示真实的**动作摘要**（读取 N 个文件 · 搜索 N 次 · 运行 N 条命令 · 思考 N 次）与首个可识别动作图标；工具次数和活动状态（运行中 / 等待 / 失败 / 未完成 / 已中断）保留在 DOM 与可访问名中。
- 默认：有运行中/等待的工作或需注意的失败/中断保持展开；正常完成且已结束时可折叠。用户显式选择优先，按模式与会话记忆；查看详情、选中文字或聚焦其中内容时不会自动收起。
- 有轮次时间证据时，即使只有一条工作也归入同一个耗时折叠，不再额外叠第二层记录；没有可信时间证据时，单条思考或单个工具保持自己的原生披露。
- 工作行按 T3 Code 的 WorkLog 密度呈现：24px 行高、24px 图标槽内 16px 图形、14px 次级文字、6px 间距、行尾折叠箭头。成功行不画绿点、不重复「已完成 0.5s」；失败与未完成用图标颜色和可访问状态文本表达；耗时默认隐藏，hover / 键盘 focus 时在行尾显示。
- 工具行保持单行摘要（语义名、参数摘要）；参数、输出和错误在行内详情中查看。动作名不收缩，长参数 / 路径吸收截断，状态图标与行尾箭头固定宽度。Runtime 的受限投影继续显示「当前视图无权读取原始参数与输出」，不暴露原始载荷。空参数行仍保留弹性占位，箭头不会贴到标题后面。
- 中间进展正文与最终回答同为 14px 阅读字号，靠次级颜色和所在位置区分；最终回答保持可见。用户补充输入始终可见，不折进工作记录；每个补充段的耗时从这条真实输入开始，到该段最后一项真实工作结束，不把后段的耗时算进前段。
- 被记录接管的原生组头隐藏，由可见记录头承担披露；原生计数仍按实际批次成员计算，P5 临时借用详情节点不会把次数算少。
- 折叠只隐藏工作内容：User、Plan、最终回答、审批、等待输入和错误终态仍在折叠之外。P5 的 compaction 是 `kind=compaction` 的 activity 工作行，按真实顺序随所属段折叠，展开后仍可读；没有照搬 T3 的 compaction 分隔行或额外卡片。后台子代理完成若以独立用户 / 系统消息到达，按真实边界留在折叠之外；它的迟到活动不延长已结算耗时。失败 / 中断通过图标和标题后缀表达，不画独立状态卡，也不把单个工具失败升级为整轮失败。
- 完成的轮次不再额外占一行「已完成 · N 次工具」；停止 / 失败 / 未完成才保留一行 24px 终态文字，时长与工具计数仍在 DOM 中可访问。轮次用量只出现在助手的操作栏：一枚低干扰统计图标，hover / 键盘 focus 给出「查看用量」，点击打开固定定位的轻量 Popover；Popover 展示整轮汇总字段、逐响应明细、模型与真实耗时，流式中标注仍在累计。缺失字段不补 0，真实 0 保留；推理是输出的子集，标注「含在输出中」。没有可信用量时不创建入口，也不恢复旧的 Token 页脚、明细箭头或等价常驻入口。
- 消息操作栏在正文下方保留固定 24px 槽位：用户消息右对齐到气泡尾部，助手消息沿阅读边左对齐；按钮 24px 命中区、16px 图形、2px 间距，默认 `opacity: 0`，消息 hover / `focus-within` 时显示，`pointer-events` 随之启用。显隐不改变消息高度、下一条位置或滚动位置；指针从正文移到操作栏不会把按钮藏掉。图标按钮共用设计系统 Tooltip（消息栏内向下弹出，避免盖住刚读完的正文），不使用原生 `title`。显式展开/收起动画与操作栏的按钮语义保持不变。

耗时来自真实墙钟：优先使用 P5 回合的 `timing`，原生回退使用消息与工具时间戳；并行工具取最晚结束而不是相加，settled 后写定，重开会话从历史时间戳恢复而不是继续计时。背景子代理在回合结束后的活动不会延长已结算的耗时。展开 / 收起通过 `preserveScrollAround` 保持触发行位置，避免可见跳动。

## 任务列表（gui_plan）

计划来自 Pi 扩展 `extensions/pi-gui-plan` 注册的 `gui_plan` 工具，不从工具调用次数、时长或正文推断。每次调用提交**完整**任务列表：id 稳定，状态只有 `pending` / `in_progress` / `completed` / `failed` / `cancelled`；扩展拒绝重复 id、空列表和未知状态。同一轮重新规划时，模型漏掉的已完成 / 失败 / 已取消任务会由扩展保留并标 `retained`；新一轮用户任务不继承上一轮完成项。工具结果 `details` 随会话持久化。计划工具不进入 Tool Timeline，避免同一件事出现两次。

**回合边界只认 Pi 的真实事件。** `agent_settled` 在整个 session 级 run 收尾时发出，自动重试、压缩、steering/follow-up 都在它之前跑完；运行中追加用户消息不会发新的 `agent_start`。因此「上一轮已 settled 后的 `agent_start`」才是新任务边界：此时切换当前计划指针，旧计划卡仍留在时间线里；运行中的 steer / follow-up、自动重试和压缩都不清空当前计划。Runtime store 与 Classic 的 `plan-live.js` 共用这条判据，不用「看到一条 user 消息」猜新回合。

`gui_plan` 的 `details` 带可选的 `turnId`：扩展在 settled 之后的新用户回合生成一次，运行中的 steer / follow-up 复用同一个 id。历史恢复按同一 `turnId` 归并计划更新，不同 `turnId` 即使复用相同任务 id 也保持两张卡；旧记录没有 `turnId` 时只能按用户消息分组，历史状态行会明确标注「计划归属不确定」，不按时间间隔或消息数量推断新运行。

## Runtime 执行时间线

Runtime 的计划、思考、工具与正文不再分散在输出区外的固定槽位，而是进入同一个 `.rtc-output` 滚动容器，按真实事件/消息顺序排列。实时顺序来自 store 收到事件的先后（不按类别重排）；历史顺序来自原生 JSONL 的 message/content 顺序。视图只按投影出的有界 block 列表放置节点，节点按 block id 复用，流式更新不重建整条时间线。

`public/runtime-timeline.js` 是实时与历史共用的纯投影：只保留用户/助手文本、真实 thinking 文本、工具名/状态/耗时、计划白名单字段和扩展写入的 `turnId`；工具原始 args、result 正文、环境变量与凭据不进入投影。历史读取用同一个投影，因此恢复的计划、思考、工具与最终回答都来自真实记录；缺字段就省略，记录被截断时状态行明确说明，不伪造内容。运行边界要么来自 `gui_plan` 的 `turnId`（`verified`），要么只能退回用户消息分组（`unknown`）；`mixed` 表示新旧记录混用，状态行同样会说明部分计划归属不确定。展开状态按会话保存：Thinking 和多项工具组默认折叠；含运行中/等待或失败的工作组默认展开，以显示真实过程。用户展开后，新工具、流式增量和切换会话都不会把它收回。

实时 `message_end` 的 `content` 是这条 assistant 消息的权威内容：缺少流式增量时，正文与 Thinking 按真实 `content` 顺序补建 block；已有流式 block 复用原节点并覆盖为权威文本，用户已展开的 Thinking 不会因结束事件被收回。同一条消息内正文与 Thinking 多次交错时，每一段保持自己的位置，不把后面的内容并回前面；连续补建的多个缺失段按 `content` 顺序依次接在前一段之后（前一段可能也是刚补建的节点），不会堆到同一个已有锚点的一侧。工具调用是真实的 `content` 分段边界，工具两侧的同类文本不会合并；但工具节点只由真实 `tool_execution_*` 事件创建和定位，`message_end` 不创建尚未执行的工具，也不移动已经出现的工具组；两者信息冲突时，工具保留先发生的真实事件位置，正文/Thinking 围绕已存在的段补齐。

回到底部按钮只操作当前会话自己的 `.rtc-output`，不共享滚动位置，也不强制把正在阅读历史的用户拉回底部；点击后才恢复 follow-latest。任务列表、工具组、Thinking 与正文的视觉 token 与 Classic 一致。

Runtime 与 Classic 共用工作记录：连续过程按真实 block 顺序合成一条记录，Plan、最终回答与轮次终态独立保留。P5 已验证时间线把原生进展节点与实际活动行按真实时序混排，搜索或导航会先展开所在记录再测量落点；恢复的工具顺序只有在与原生通道工具名逐一相符时才会被采纳。

`public/plan-model.js` 只做契约校验与按回合归并，`public/plan-view.js` 只认归一后的 plan；按稳定 id 复用行，只改变化的文字/状态/顺序。默认展开，用户折叠后流式更新不改变折叠状态；头部显示真实的 `已完成/总数`。执行结束但仍有 `in_progress` 时，数据状态不变，展示文案改为「未完成」并停止呼吸动画，不伪造 `completed`。

## 回到底部

`public/scroll-button.js` 给 Classic 的 `#stream` 与 Runtime 的 `.rtc-output` 各建一个按钮，只对传入的滚动容器写 `scrollTop`，从不调用 `document` / `window` 的通用滚动。离底超过 160px 出现，回到 8px 以内消失（两段阈值防抖）。运行中复用 `thinking-dots` 的四点/三点动画，悬停或键盘聚焦时换成下箭头，两个图标叠在同一网格，按钮尺寸不变；闲置时直接显示下箭头。点击后平滑回到底部，并在短 follow 窗口结束时再补一次到底，覆盖流式连续追加；用户滚轮 / 触摸 / 方向键会立即退出 follow。`prefers-reduced-motion` 下改为瞬时滚动并关闭过渡。Runtime 切会话时按钮跟随该会话自己的 `scrollTops`，不共享其他会话的位置。

## 附件与 Minimap

文件附件在消息里是紧凑块，保留原名称、元信息和当前已有的文本详情；详情按钮可用键盘打开，不新增 PDF/Word 预览或分栏入口。多附件在 Bubble 内自然堆叠。图片继续显示现有缩略图，上传逻辑不变。

Minimap 仍按每条 User 消息建一条短线，沿用 DOM 锚点、位置缓存与点击跳转。当前项更亮，hover / focus 可见；点击后立即同步高亮，窄窗口沿用隐藏策略。它不索引 Assistant、Thinking 或 Tool，也不另存消息副本。

这一轮 UX 修复改了它的两处行为：marker **聚成一组紧凑短线**（整组纵向居中、条数与可用高度决定间距，不再按消息在内容里的比例铺满整个左栏 —— 那样一条长回答就会把后面的点推到很远）；点击跳转**只写 `#stream.scrollTop`**，不再用 `element.scrollIntoView()` —— 后者连带滚动 `overflow:hidden` 的 `.stage`，会把顶栏推出视口（详见 [sessions.md](sessions.md) 第十节）。`.stage` 同时改成 `overflow:clip`（不是可被脚本滚动的 `hidden`），`.stage-head` 有了显式背景并与 `electron/main.cjs` 的 `titleBarOverlay.color` 共用同一个 `--titlebar` 值。

## 渲染边界与验证

SSE 的增量消息与 `get_messages` 历史消息仍走 `messages.js`；Tool 的两个数据来源仍共用 `ToolEntry → tool-view.js`。流式绘制保留原限流与近底部自动滚动规则；最终内容只更新变化的块并复用现存 Thinking 节点。长代码只在 `<pre>` 内横向滚动。

`npm run test:ui` 验证 DOM 语义、折叠状态、流式结束、工具状态、附件与 Minimap；`npm run test:conversation-flow` 覆盖工作记录归并、焦点/选区、受限详情、P5 混排和 Classic/Runtime 真实渲染接入。`npm run harness` + `npm run shots:harness` 在真实 Chrome 中验证 69–85 场景，包括 700、900、1200、1536px 的阅读列和溢出。P14-A 的 57–68 场景在注入 P14-B 夹具前运行。
