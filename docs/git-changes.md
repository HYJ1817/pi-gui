# 文件变更与撤销

侧栏的「文件变更」列出**当前 Git 工作区**里相对 HEAD 有差异的文件。
定位是「看清改了什么、决定留还是撤」，**不是 IDE**。

## 一、列表

`M` 修改 / `A` 新增 / `D` 删除 / `R` 重命名 / `C` 复制 / `U` 冲突 / `??` 未跟踪，
外加相对路径和 `+N −M` 行数。点一行就地展开 unified diff，可以「打开」或「撤销」。

Agent 执行 `write` / `edit` / `bash` 之后会**自动刷新**（防抖 450ms，
连续改多个文件只查一次 `git status`），也可以手动点「刷新」。

**刻意不做的事**：不内置代码编辑器（「打开」交给系统默认程序）、
不做 side-by-side、不做合并冲突编辑、不做 commit / push / branch 管理。

## 二、看 diff

- **按 hunk 折叠。** 每个 hunk 有一条可点击的标题栏（带该块的 `+N −M`），
  点一下折叠这一块；工具条上的按钮一键「展开全部块 / 折叠全部块」。
- **上下文可调。** 默认跟随你的 `diff.context` 配置（通常是 3 行），
  也可以切到「20 行」或「全部」。切换会**重新问后端** —— diff 正文是 git 按
  `-U` 现算的，前端没法从已截断的文本里补出被裁掉的上下文行。
- **暂存区与工作区分开显示。** `MM` 这种「既暂存又改了」的文件会给出两段，
  否则看不出到底在跟谁比。
- **有大小上限**（默认 512 KB，`PI_GUI_GIT_DIFF_MAX_BYTES` 可调），
  超了就截断并提示；二进制文件直接说明「看不了文本差异」，
  不会塞一堆乱码进界面。

## 三、只看 Agent 改的

列表上方有「全部 / 仅本次会话」两个视角。「本次会话」是 `write` / `edit`
这两个工具碰过的文件（**`bash` 改的东西推导不出来，所以不在内**），
行上会带一个「本会话」小标记。

**侧栏徽标永远是 Git 的总数**，不受这个视角影响 —— 徽标回答的是
「磁盘上有多少没提交的东西」，那是客观数字，不该被视角改变。

### 与「任务执行期间变更」的区别

Planner 的每个 task 也会记一份**执行期间观察到有变化的文件**
（`attempts[].filesChanged`，见 [workflows.md](workflows.md)）。三者别混：

| 名字 | 是什么 | 权威 |
|---|---|---|
| 侧栏「文件变更」 | 当前 Git 工作区相对 HEAD 的全部差异 | **Git**（`git status`） |
| 「仅本次会话」视角 | 本次会话里 `write` / `edit` 工具碰过的文件 | Agent 事件账本 |
| 任务「执行期间变更」 | 该 task 执行前后两次快照的差集 | 快照差集，**只覆盖那段时间** |

任务那份 `filesChanged` **只存文件名**；P10 起 attempt 上另有 `changeEvidence`，
存**这次执行前后冻结的 bounded patch**（见 [workflows.md](workflows.md) §二之二）——
那个是「那时的 diff」，不会随工作区漂移，**也补不了这个面板的位置**：想知道「现在
磁盘上到底差什么」仍然只有这一处实现。

⚠️ **两者用同一套项目边界判据**：`projectRoot` 只是某个仓库的子目录时，
同仓库 sibling 的改动既不进这个面板、也不进任务证据，路径一律是**项目相对**的。

## 四、撤销

| 文件状态 | 行为 |
|---|---|
| 工作区 `M` / `D` | `git restore -- <path>` |
| 未跟踪 `??` | 删除该文件。确认框明写「撤销将删除该文件」，按钮也是「删除文件」 |
| 已暂存 `M ` / `MM` | 拒绝；点「取消暂存并撤销」才先 `git restore --staged` 再恢复 |
| 已暂存的新增 `A ` | 取消暂存后它会变成未跟踪文件，所以**在动 index 之前**就把「会删掉它」问清楚 |
| 重命名 / 复制 `R` / `C` | 拒绝（只恢复一条腿会让文件处于半吊子状态） |
| 冲突 `U` | 拒绝，请用 git 手动解决 |

### 「全部撤销」是两段式

先干跑拿后端算出的**权威计划**（恢复几个 / 取消暂存几个 / 删几个），
摊给你看清楚再执行。有未跟踪文件时会多给一条路径「仅撤销已跟踪文件」，
因为「撤销改动」和「删掉新文件」是两个不同的意愿。

一次最多处理 200 个文件（`PI_GUI_GIT_RESTORE_ALL_MAX` 可调），
**超了就整体拒绝**而不是撤销到一半停住。

## 五、几条设计取舍

- **以 Git 为准。** 界面上的数字来自 `git status`，不是「Agent 声称改过什么」。
  两者会不一致（Agent 改了又自己撤回、或者你手动 revert 过），这时以 Git 为准。
- **不是 Git 仓库不是错误。** Pi GUI 允许打开普通文件夹，那种情况下聊天、
  改代码、跑命令全部照常，只是没有变更信息 —— 界面给一句中性说明，
  不弹错、不自动 `git init`。
- **两条写权限默认关闭。** 删未跟踪文件（`deleteUntracked`）和取消暂存
  （`unstage`）都必须由用户明确授权才生效。没有授权时后端一个字都不动，
  而是把「还需要什么授权」原样返回给界面 —— 所以不存在「静默改了 index」
  这种状态。
- **批量撤销逐条走同一条动作路径**，不用 `git checkout .` /
  `git reset --hard` / `git clean -fd`。于是「哪些文件不该被自动撤销」
  只有一处答案。这几条禁令有自动化守卫盯着（`tests/git.cjs` 第 15 段）。

## 六、命令怎么执行

所有 Git 命令都指定项目目录、走**参数数组**、`shell: false`，
路径经 `lib/safe-path.js` 校验（`../`、绝对路径、符号链接 / junction 逃逸
一律拒绝），并带超时与输出字节上限。

相关环境变量：

| 变量 | 作用 | 默认 |
|---|---|---|
| `PI_GUI_GIT_TIMEOUT_MS` | 单条 git 命令超时 | 见 `lib/git.js` |
| `PI_GUI_GIT_DIFF_MAX_BYTES` | diff 正文上限 | 512 KB |
| `PI_GUI_GIT_STATUS_MAX_BYTES` | `git status` 输出上限 | 见 `lib/git.js` |
| `PI_GUI_GIT_UNTRACKED_MAX` | 未跟踪文件列举上限 | 见 `lib/git.js` |
| `PI_GUI_GIT_RESTORE_ALL_MAX` | 一次「全部撤销」最多处理几个文件 | 200 |

## 九、行级评论持久化（T3-B）

在 Changes 的 Diff 行号上添加、修改或删除评论，只有后端确认落盘后才显示成功。
评论按当前工作区和会话隔离；打开面板后按需恢复，不自动展开其他文件。
恢复的锚点先显示“待重新确认”，读取当前完整 Diff 后沿用 T3-A 的定位规则；
行内容变化、文件不再出现在变更列表时保留评论并标记原位置已变化。
隐藏上下文保持待确认，截断 Diff 不能证明位置有效或已经消失。

保存失败保留编辑正文；版本冲突不覆盖磁盘，使用“重新加载评论”保留当前编辑框草稿，
再由用户决定是否重新保存。关闭面板或切换会话会丢弃未保存草稿，不跨重启恢复。
复制和填入当前会话仍须用户点击，填入只追加草稿，不发送给 Agent。

数据位于后端指定的 `<DATA_DIR>/review-comments/<scopeHash>.json`，不写项目、Git、Pi JSONL 或 Planner。
Electron 默认使用应用 userData；源码默认 data 位于源码目录，因此评论存储会安全拒绝。
源码运行须先显式设置项目外、已存在的专用 `PI_GUI_DATA` 后重启；这会沿用原有全局 data 语义，
不自动搬迁其他应用数据。没有可独立确认的原生磁盘会话时，恢复暂不可用，待身份确认后重试。

首版 schema v1；T3-C 兼容升级见下节。每作用域 200 条、每条 2000 字，文件上限 2 MiB；
最多 20 个磁盘作用域，删除后的空 revision 记录也计入上限，不能自动清除以免迟到写入复活。
正文只通过本机认证 API 传输；不附带代码 snippet、完整 Diff、绝对路径或运行时句柄。
安全与故障恢复见 [security.md](security.md#t3-b-评论存储边界)，设计与实测见
[T3-B 设计](T3-B-plan.md) 和 [T3-B 验收](T3-B-acceptance.md)。T3-A 验收保留为历史记录。

## 十、多行区间评论（T3-C）

点击行号仍打开单行评论；随后 Shift 点击另一个行号选择区间，键盘可用 Shift+Enter/Space。
选区显示轻量「添加区间评论」，确认后进入编辑器；Esc 取消选区。
只接受同一文件、同一分区、同一完整 hunk 内的 2～20 个代码行。
二进制、截断、hunk 计数不完整、缺失坐标或跨块的内容不能选择。
普通单行入口保留 T3-A 兼容行为，不将新的完整 hunk 限制套到旧单行评论上。

区间保留有序的每行类型、旧/新行号与哈希，不存源代码；首行字段沿用旧锚点，
`range: {version:1, lines:[{type,oldLine,newLine,codeHash}]}` 扩展区间证据。
上下文行两侧都有坐标，新增行只有新坐标，删除行只有旧坐标。
汇总/反馈分别表达真实的两侧行号，混合增删时同时标注 Diff 行数；不将视觉行数当成文件行数。
区间从其独立标记编辑，单行从行号编辑；可在相同首行共存。区间之间任一侧坐标重叠即拒绝新增，
包括过期区间；先处理或删除原意见。同一选区再次添加会打开原评论。

恢复只在原坐标核对全部哈希，要求唯一、连续、同一完整 hunk，不按相似文本搜索其他位置。
内部代码变化或无法唯一核对则标记「原位置已变化」；只有缺失上下文、已看到的证据一致且
改动指纹与最近完整确认一致时保持「待重新确认」。折叠、缩放不迁移评论。
刷新期间保留有效编辑器的正文，迟到的旧 Diff/保存响应不能回写新的界面或作用域。
过期评论仍可查看、复制、删除；填入只追加当前会话草稿，不自动发送或执行。

v1 单行数据读取不写盘，继续可编辑删除；单行保存保持 v1。第一次保存区间时，
在原排他事务锁和 revision CAS 内原子替换为 disk v2，保留原评论 ID、正文、时间和锚点。
升级后即使删空也保持 v2 与 revision；不自动降级。写入/flush/rename 失败保留原有效文件，
丢失确认须重新加载，未知未来版本拒绝覆盖。scope 身份与 API 路径不变。
回滚到只支持 v1 的旧版会拒绝读取已升级的 v2；保留原件，恢复 T3-C 后可重读，勿强行改版本号。
设计与数字见 [T3-C 方案](T3-C-plan.md)、[T3-C 验收](T3-C-acceptance.md)。

## 十一、准备修改任务（T4-A）

在「审查意见」内点击「准备修改任务」，按文件勾选单行或区间意见，再预览完整任务。
默认仅选择由当前完整 Diff 确认的意见；过期/待确认意见显示原因与原文，但不能纳入。
同一位置的单行与区间仍是两条意见。全选/取消/返回调整仅改变弹窗内选择，不保存评论。

任务按文件归组，逐条保留分区、准确的旧/新坐标、原文和确认状态。混合暂存区/工作区会提示；
路径、会话、意见作为 JSON 字符串引用数据，不解释为生成器指令。与原反馈共享 12000 字上限，
超限整体拒绝并要求减少选择，不静默截断。预览只是拟交给 Agent 的任务，未生成代码或实际 Git Diff。

复制和填入前核对 scope、项目/实际 Worktree、会话/owner、workspace generation、存储 revision、
所选评论快照与临时 Diff 证据代号。刷新尚在进行时禁止生成；评论或证据变化即清空旧任务并禁用交付，
须返回重新生成。项目/会话切换沿原生命周期立即关闭弹窗；已脱离的旧按钮不能写入其他会话。

填入复用现有 `review-fill.js`：只追加可写的当前会话输入框，保留原草稿，不发送、不触发 Agent。
填入本身不会改代码，但用户之后发送的任务可能由 Agent 在真实工作区执行；文本约束不是文件写入隔离。
没有新存储、schema/稳定 scope/区间匹配变更，也不执行 Git、Pi RPC、Planner 或补丁操作。
方案见 [T4-A 计划](T4-A-plan.md)，实测证据见 [T4-A 验收](T4-A-acceptance.md)。

## 十二、候选修改（T4-B）

修改任务预览中的「在隔离工作区生成修改」先只读预检，用户明确确认后才创建受控候选 Worktree、
沿既有独立会话启动 Agent。原工具审批和 Stop 保留；审批可从「打开候选会话查看审批」进入。
结束后在同一弹窗查看输入快照到实际文件的 Diff，原项目已有 dirty 不计作本次修改。
「候选修改」可重开保留结果；关闭面板不删除代码，也不会重发任务。没有应用到原项目的按钮。

第一版拒绝来源 untracked 和不能完整核实的 Git/路径/容量状态。未知工具、外部变化等会明确标为结果无法可靠确认。
Worktree 不是 OS 沙箱，不能阻止同用户 Agent 通过其他路径访问原项目。
支持范围、私有材料及崩溃锁处理只见 [T4-B 设计](T4-B-design.md)，实测与审查状态见 [验收记录](T4-B-acceptance.md)。

## 十三、候选采纳条件检查（T4-C1）

保留结果的弹窗提供“检查采纳条件（只读）”。新记录保存三份身份观察与历史 Diff 摘要，
后端重新读取来源、候选，核对完整内容、逻辑 index、Git/文件/目录身份，并显示整次新增/修改/删除清单。
来源有新修改、候选漂移、未确认副作用、ignored、锁或身份不明均拒绝，不自动合并或覆盖。
旧候选缺少关键身份材料仍可看 Diff，但暂不支持安全采纳检查。

当前只有 C1：即使本次读取未发现冲突，仍明确显示“暂不可采纳”。没有写入 nonce 或确认采纳按钮，
不修改源码、暂存区、T4-B 历史或创建提交；重开须重新检查，迟到响应不能越过会话/弹窗生命周期。
C2 尚无符合安全要求的生产写入与多文件恢复机制，不用普通复制、patch 或 limited writer 替代。
具体边界见 [设计](T4-C-design.md)及[验收](T4-C-acceptance.md)。

## T4-C2 当前采纳流程

以上 T4-C1 段落为历史只读阶段。当前从候选真实 Diff 点击“准备采纳修改”，核对来源与文件范围后明确“确认采纳”。后端重新核验并在 Windows 本地 NTFS 受控写入 working tree，index 保持原状。失败不自动回滚，恢复须另行预检和确认；身份或内容未知时保留材料并要求人工核实。平台限制与验收见 [T4-C 设计](T4-C-design.md)及[验收](T4-C-acceptance.md)。
