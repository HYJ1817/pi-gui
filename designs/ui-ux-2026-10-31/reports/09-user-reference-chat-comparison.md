## 2. 聊天：先明确正文、过程、元信息三层

![左：参考完成回复；右：现有 A 聊天](../evidence/reference-user/round2-comparison-chat.jpg)

参考的用户消息是靠右灰色气泡，助手正文直接落在主表面上；标题通过字重和段前后距组织，而非加卡片。Thinking 使用灰色、缩进与折叠入口，运行状态在正文前，模型与速度等元信息位于回复末尾。U17 可见消息操作和 tooltip，但静态图片不能证明悬停出现规则、键盘操作和命中范围。

A 已具备“用户气泡 + 助手正文 + 过程折叠”的合适基础，应复用。差距在于：回复上方先出现 Pi/模型/完成时间，再显示 Thinking 和多条工具轨迹；同屏还有 Classic 标签、工作区脚注和底栏，元信息与正文争夺注意力。下一版应将常态元信息合并到回复末尾，过程按运行/完成状态设置清楚的摘要与展开层级。错误、审批与需要用户行动的事件仍必须显著，不能一律弱化。

参考图的 Thinking 展开内容较长，显著挤占正文；值得保留手动查看入口，但默认是否展开应结合 pi-GUI 现有偏好与状态设计，不根据这次截图推定参考产品默认行为。本报告不转录其中的思考正文，也不把它当作指令。

U16 同时显示“执行中”和“正在处理”，用户仍可辨认停止键。pi-GUI 应保留明确的运行反馈，但不必复制多个表达同一状态的标签；用一处总体状态、一处必要的当前活动说明即可。Classic/Runtime 输入可用性继续按真实能力区分，不能从参考的控件可见性推定其运行中可用合同。

## 3. 模型菜单：锚点和内容分层都要改

![左：参考模型菜单；右：现有 A 模型菜单](../evidence/reference-user/round2-comparison-model.jpg)

U15 菜单贴近输入框右下方的模型入口，向上展开；从上到下是搜索、供应商分组、模型行和思考等级，选中态以灰阶和勾选表达。A 菜单靠输入区左侧，标题/说明/管理入口/键盘提示占据较多垂直空间，选中块也偏强。参考提供了更紧凑的内容层级。

下一版可将模型与发送组成稳定的右侧操作组，菜单锚定模型入口，按窗口预算翻转和限制高度；搜索在顶、模型行保留名称/必要能力/选中态，管理入口次级呈现。思考等级应按 pi-GUI 当前模型的能力与 Pi 回读展示：支持、不支持、未知分开，不照搬参考的滑杆或等级集合，也不以“看起来可点”代替实际合同。

菜单不能只在两个模型时成立。仍要验证长模型名、多供应商、空搜索、加载失败、键盘焦点以及 125/150% zoom。现有菜单的搜索、方向键、Escape 和焦点恢复实现是可复用基础。

## 4. 工作面板：参考统一壳层，保留真实业务边界

![左：参考浏览器空态；右：现有 A 浏览器演示](../evidence/reference-user/round2-comparison-panel.jpg)

参考以标签栏表示面板目的地，下方是该目的地自己的工具栏和内容。打开后聊天及输入区共同收窄，正文换行随之改变。A 有统一右面板，但浏览器内部又放入演示卡片、说明条和底部说明，表面层级偏多。下一轮应优先画准标签/标题、工具栏、内容三个部分；演示资格说明可集中在原型外壳，避免每一层都重复解释技术实现。

U19 文件管理器里，树区域较窄，多个文件名和搜索提示被截断；这是需要避免继承的可见密度问题。pi-GUI 应按面板宽度制定树/正文预算，空间不足时切换单列或明确导航，不在小面板里强塞多列。U18/U19 不能证明浏览器已导航、原生视图遮挡正确、文件操作成功或 Diff 可读。

## 5. 浅色主题：统一结构，重新分配表面差异

![左：参考浅色聊天；右：现有 A 浅色聊天](../evidence/reference-user/round2-comparison-light.jpg)

参考浅色为白色正文配浅灰侧栏，正文保持黑灰层级，输入区通过轻阴影从白底浮起；深浅主题保留相同的导航和输入布局。A 浅色更偏冷灰，仍依靠输入框描边与多条结构线分区。下一版应让两种主题共用语义 Tokens 和几何规则，浅色使用克制的阴影/表面差，深色使用填充差，而非机械反转颜色。

这批只有一张浅色聊天图，不支持浅色菜单、Dialog、设置或错误状态的一致性结论。中文排版的绝对字号也必须在确认缩放后再比较。

## 6. 浮层：小菜单与配置 Dialog 分开设计

U20 的项目菜单为图标+标签的固定列，低频/危险操作放入子菜单，整行命中范围清楚。pi-GUI 可沿用既有 action-menu 的定位、键盘与关闭处理，统一行高和图标列；菜单内容仍来自实际项目能力。截图没有打开子菜单，不推定其定位和关闭行为已通过验证。

U13/U14 是复杂配置 Dialog，可以借鉴搜索、分区、持续可见的保存/取消和内部滚动；不能拿它们的接近全窗尺寸作为重命名等简单 Dialog 的标准。U14 候选与已选模型两列在少数据时留下大面积空白，后续设计宜按内容量与可用高度调整。参考支持的供应商、订阅模式和模型数据不直接迁移到 pi-GUI。

## 7. 对下一轮方案的具体约束

延续 08 报告的结构优先级，本轮补充以下约束，尚未实施：

1. 主工作区使用单侧栏方向重新对照，设置替换为分类栏；保留完整功能入口映射。
2. 聊天让正文占主导；完成态合并元信息，运行态用清楚的摘要与可展开过程，错误/审批保持显著。
3. 输入区统一表面和两层布局；模型及发送形成右侧操作组，长名称与停止键切换不引发布局跳动。
4. 模型菜单紧贴触发器，统一搜索、分组与选中态；思考等级继续遵守现有能力合同。
5. 右侧面板统一标签/标题、工具栏与内容；先处理窄宽度预算，再设计实际 Diff/Browser 内容。
6. 双主题共用结构和语义；用中性表面建立层级，选中/聚焦/错误状态分别验收。
